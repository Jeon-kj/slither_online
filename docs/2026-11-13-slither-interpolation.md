# Slither 표시 보간과 Head 카메라 추적

## 배경, 문제와 요청

자기 Slither 및 봇의 움직임이 계단식으로 보였다. Head와 루트의 위치 적용 순서를
수정한 뒤에도 증상이 남았다. 사용자는 카메라를 끄면 Scene 뷰에서 움직임이
부드러워지는 것을 관찰했고, 공통의 위치 갱신 간격과 카메라 추적의 조합을
의심했다. 카메라 렌더링 부하와 추적의 영향은 계측으로 분리하지 못한 상태다.

요청 프롬프트:
> 둘 다 인 것 같아. 실제로 봇을 포함한 slither 들이 보간없이 움직이기 때문에 버벅거리며 움직이고, 카메라가 이를 따라가며 관찰하는 과정에서 버벅거림이 극대화 되는 착시가 있나봐. 먼저 slither의 움직임을 보간하고, 카메라가 오브젝트의 머리를 쫓도록 해봐.

기존에는 수신 메시지를 처리할 때 Head, 몸통, 회전을 즉시 바꿨다.
수신이 없는 렌더 프레임에는 같은 위치를 유지하며, 메시지가 몰리면 중간 위치는
화면에 표시되지 않았다. 카메라는 루트를 추적했다.

## 변경과 호출 순서

- `SltherContext.cs`: 수신 목표 Head 위치·각도, 몸통별 목표 위치를 저장한다.
  `Render(deltaTime)`에서 `1 - exp(-20 * deltaTime)` 비율로 매 프레임 보간한다.
  회전에는 `LerpAngle`을 사용한다. 부모 루트를 옮긴 뒤 Head 위치를 맞추며,
  몸통 보간 시 부모 이동량을 빼서 이전 월드 좌표를 복원한다.
- `SlitherManager.cs`: `UpdateSlitherPos()`와 `UpdateSlitherHeadAngle()`은
  Transform 대신 목표값을 갱신한다. `LateUpdate()`에서 모든 Slither를 그린다.
  몸통 추가·제거 시 목표 배열도 같은 개수로 맞춘다.
- `GameManager.cs`: 입력 대상은 기존 루트로 유지하고 카메라 대상은 Head로 전달한다.
- `CameraFollowTarget.cs`: 실행 순서 100을 지정한다. 기본 실행 순서의
  SlitherManager가 보간을 끝낸 뒤 같은 프레임의 Head를 추적한다.

호출 순서:

1. 수신 스레드 → recvQueue.
2. NetworkManager.Update → MessageHandler → MainThreadDispatcher.Update.
3. 수신 좌표로 기존 경로와 몸통 목표를 계산한다.
4. SlitherManager.LateUpdate → SlitherContext.Render.
5. CameraFollowTarget.LateUpdate → 보간된 Head 추적.

서버, 프로토콜, 서버 상태 갱신 순서는 변경하지 않았다.
이 방식은 과거 스냅샷을 일정 시간 지연해 재생하는 버퍼가 아니라 최신 목표에
지수적으로 수렴하는 표시 보간이다. 시간 상수는 50ms이며, 고정 목표까지 약
150ms에 95% 수렴한다. 표시 지연이 추가되며 통신 단절 중에는 마지막 목표에서
멈춘다. 원래 서버 경로 데이터는 표시 보간에 의해 변경되지 않는다.
로컬 충돌 보고가 관찰하는 위치도 보간된 표시 좌표가 되지만 서버의 충돌 판정은
그대로다. 급회전에서는 보간 특성상 표시 궤적이 원래 경로의 모서리를 줄일 수 있다.

## 재현과 에디터 확인

1. 동일한 서버와 씬에서 사람 클라이언트 및 봇을 접속한다.
2. 클릭하지 않고 마우스를 고정해 Game/Scene 뷰에서 직진을 비교한다.
3. 마우스 방향을 바꾸어 머리 회전과 몸통 이동이 함께 부드럽게 이어지는지 본다.
4. 카메라가 Head를 추적하고, 추적을 끈 경우에도 각 Slither가 보간되는지 본다.
5. 성장·부스트에 따른 몸통 추가/제거와 사망 시 예외나 몸통 끌림이 없는지 본다.
6. Profiler에서 프레임 지연을 별도로 확인한다. 표시 보간은 렌더링 부하나 긴
   프레임 자체를 해결하지 않는다.

## 실행한 검증과 한계

Unity와 C# 컴파일러가 환경에 없어 Unity 컴파일·Play 모드·물리 동기화 및 실제
화면 비교는 실행하지 못했다. 서버는 수정하지 않았다. `git diff --check`는 통과했다.

기존 실제 수신 좌표를 사용한 Python 수치 모델에서 수정 전 즉시 적용과 수정 후
보간을 같은 좌표열과 60/144fps 조건으로 비교했다. 실제 성능 측정은 아니다.

- 수신자 2개와 Slither 2개, 각 195~196개 좌표열 모두에서 정지 프레임 및 최대
  프레임 이동량이 감소했다.
- 대표 60fps 결과: 정지 프레임 105 → 1, 최대 프레임 이동량 약 0.078 → 0.0315.
  시작 직후 아직 이동 목표가 도착하지 않은 프레임도 집계했다.
- 부모 이동 중 고정된 몸통 좌표 유지, 머리/몸통의 직선 간격 유지, deltaTime=0,
  긴 프레임에서 목표 초과 방지, 30/60/144fps 고정 목표 수렴을 확인했다.
- 각도 359° → 1°의 짧은 회전 경로를 수치 확인했다. Unity API 실행 검증은 아니다.

재실행 명령: `python3 /tmp/slither-smoothing-check.py`

원본 결과 및 스크립트(임시 파일이므로 환경 정리 시 삭제될 수 있음):

- `/tmp/slither-motion-probe.json`: 이전 서버 실험의 실제 수신 좌표.
- `/tmp/slither-smoothing-check.py`: 소스 연결 검사 및 보간 수치 모델.
- `/tmp/slither-smoothing-check.json`: 전후 비교 결과.

실제 체감 개선과 프레임 성능 개선은 아직 검증하지 않았다.
