# Slither 움직임 끊김 해결

## 문제 요약

Unity의 Game·Scene 뷰에서 내 Slither가 끊겨 보이고, 같은 화면의 봇은 상대적으로
부드러워 보였다.

### 문제 발생 조건

- 수정 전 버전에서 서버 실행 후 Unity 클라이언트 접속
- 내 Slither를 움직이며 Game 뷰 또는 Scene 뷰에서 관찰
- 마우스를 고정한 상태에서도 위치가 뚝뚝 끊겨 변하는 현상 발생
- 같은 클라이언트 화면의 봇 Slither는 상대적으로 끊김이 덜 보였음(착시였을 가능성 있음)
- 카메라를 켠 상태에서 관찰됐으며, 카메라를 끄면 Scene 뷰의 움직임이 부드러워졌다는 사용자 보고

## 원인 및 해결

수신 좌표를 보간 없이 즉시 적용해 이동이 계단식으로 표시됐다. 카메라 추적이
끊김을 더 두드러지게 한다는 관찰을 바탕으로, 머리·몸통·회전을 매 프레임 보간하고
카메라가 보간된 Head를 추적하도록 변경해 해결했다.
별도로 발견한 Head·루트 중복 이동 오류도 수정했다.

## 해결 과정

### 1. 분석 요청과 최초 답변

**사용자 요청**

- 내 Slither와 봇의 입력·서버 처리·위치 수신·화면 적용 경로 비교 요청
- 서버·수신·화면 반영 중 끊김이 시작되는 단계 확인 요청
- 코드 수정 없이 분석만 진행하도록 요청

**결과**

- 두 Slither의 수신·위치 적용 경로가 같음을 확인했음
- 수신 좌표를 보간 없이 즉시 적용하는 구조 확인
- Head 이동 후 부모 루트를 옮겨 이동량이 중복되는 별도 오류 발견
- 서버 실험에서 좌표 간 이동량은 일정했으나 수신 간격 변동 확인

### 2. 로컬과 봇의 차이를 중심으로 가설 정리

**사용자 요청**

- 내 Slither가 봇보다 더 끊기는 이유를 가능성 순으로 정리하도록 요청

**결과**

- 사람 입력 변화, 카메라와 입력의 상호작용, Head·루트 좌표 불일치를 후보로 제시했음
- 부스트, 충돌 보고, 공통의 보간 부재도 후보에 포함했음

**사용자 후속 요청**

- 마우스 고정 및 Scene 뷰에서도 발생한다는 관찰 전달
- 입력·카메라·부스트·충돌 보고 후보 제외 요청

**결과**

- 공통 코드의 오류만으로 로컬·봇 차이를 설명하기 어렵다는 점 인정
- 실제 오브젝트 구성, 수신 좌표열 및 적용 좌표 차이를 확인하는 방향 제시

### 3. 첫 수정과 실패

**사용자 요청**

- Head·루트 적용 순서 문제를 후보로 유지한 재탐색 요청
- 추가 원인이 없으면 해당 오류부터 수정하고 검증하도록 요청

**결과**

- 같은 프리팹과 위치 적용 경로를 사용함을 재확인했음
- 별도로 Slither를 이동시키는 스크립트는 발견하지 못했음
- 루트 → Head 순서로 위치를 적용하도록 수정했음
- 사용자 확인 결과 실제 끊김은 남아 있었음 — 첫 수정만으로 해결 실패

### 4. 카메라 관찰에 따른 조사 방향 변경

**사용자 요청·관찰**

- 카메라를 끄면 Scene 뷰의 움직임이 부드러워진다는 단서 전달
- 카메라 원인 가능성 재제기

**결과**

- Scene 뷰에서도 보인다는 이유로 카메라 가능성을 낮춘 판단 수정
- 카메라 이동에 따른 마우스 월드 좌표 변화와 렌더링 부하를 구분해 설명했음
- 추적 컴포넌트와 Camera 컴포넌트를 각각 끄는 비교 제안

### 5. 보간·Head 추적 수정과 성공

**사용자 요청**

- 모든 Slither의 보간 없는 움직임이 카메라 추적과 겹쳐 더 끊겨 보인다는 가설 제시
- Slither 움직임 보간 및 카메라의 Head 추적 요청

**결과**

- 수신 시 목표값을 저장하고 머리·몸통·회전을 매 프레임 보간하도록 변경했음
- 카메라 추적 대상을 루트에서 보간된 Head로 변경했음
- 사용자 “좋아 해결되었어.” 응답으로 실제 환경의 증상 해결 확인

## 조언

- **후보 제외 근거를 더 좁게 해석할 필요:** 마우스 고정은 입력 좌표가 일정함을
  보장하지 않으며, Scene 뷰에서 보인다는 사실도 카메라의 입력 계산 영향이나
  렌더링 부하를 배제하지 못함. 같은 송수신 형식 역시 실제 좌표열과 도착 간격이
  같다는 근거는 아님. 후보 제외 요청을 그대로 받아들이기보다, 관찰로 배제되는
  범위와 아직 남는 가능성을 설명하고 비교 실험을 제안하는 편이 나았음.
- **별도 오류와 주된 증상의 인과관계 구분:** Head·루트 오류는 공통 경로에 있어
  로컬만 더 끊기는 차이를 단독으로 설명하기 어려웠음. 좌표 오류 수정과 끊김 해결을
  분리하고, 같은 화면의 수신 좌표·표시 좌표·프레임 시간을 먼저 비교하는 방향 권장.
- **변경을 나눠 비교:** 카메라 추적만 끄기, Camera 컴포넌트만 끄기, 보간만 적용하기,
  Head 추적까지 적용하기를 차례로 비교하면 원인과 각 변경의 효과를 구분하기 쉬움.

## 변경 파일

경로 기준: `client_unity/slither_online/Assets/Script/`

| 파일 | 변경 내용 |
|---|---|
| `SltherContext.cs` | 즉시 위치 적용을 머리·몸통·회전 보간으로 변경하고 부모 이동량 중복을 보정했다. |
| `SlitherManager.cs` | 수신 시 목표값을 저장하고 매 프레임 표시 위치를 갱신하도록 변경했다. |
| `GameManager.cs` | 카메라 추적 대상을 루트에서 Head로 변경했다. |
| `CameraFollowTarget.cs` | Slither 보간 후 카메라가 갱신되도록 실행 순서를 지정했다. |

## 확인 결과

- 수치 모델에서 Head 중복 이동 보정과 표시 보간 검증 및 diff 검사 통과
- 보간·Head 추적 적용 후 사용자가 실제 환경에서 증상 해결 확인
- 작업 환경에 Unity가 없어 직접 컴파일·화면 검증은 수행하지 못했음
- 보간과 카메라 변경의 개별 기여도, 카메라 렌더링 부하와 추적의 영향은 분리 측정하지 못했음
- 보간에 따른 짧은 표시 지연 추가
