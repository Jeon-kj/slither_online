# boost_status 데이터 경합 해결

## 문제 요약

네트워크 스레드는 일반 bool인 `boost_status`를 잠금 없이 변경하고 게임 스레드는
mutex를 보유한 상태에서 읽어, 두 접근 사이의 동기화가 보장되지 않았다.

### 문제 발생 조건

- 코드 확인: 네트워크 스레드의 부스트 메시지 처리와 게임 스레드의 이동 처리 병행
- 코드 확인: 메시지 추출의 잠금 해제 후 부스트 핸들러 호출
- 실제 플레이 중 오동작이나 충돌 증상은 직접 재현하지 않았음

## 원인 및 해결

읽는 쪽만 mutex를 사용해 쓰기와 읽기가 상호 배제되지 않았다. 쓰기 경로에서도
기존 `server_mutex`를 잡고 클라이언트 조회와 상태 갱신을 수행하도록 변경했다.
삭제된 클라이언트는 무시하며, `operator[]`에 의한 항목 재생성도 방지했다.

## 해결 과정

### 1. 경합 검증과 개념 확인

**사용자 요청**

- 별도 worktree 추가 및 boost_status의 동기화 필요성 검증 요청
- 이전 값이나 새 값 어느 쪽을 읽어도 되는 상황에서 경합이 문제인 이유 설명 요청

**결과**

- 일반 bool의 읽기·쓰기 사이에 동기화가 없는 실제 호출 경로 확인
- 값 반영이 한 틱 늦어도 되는 요구와 C++ 데이터 경합의 안전성 구분
- bool의 atomic 전환만으로 클라이언트 컨테이너와 객체 수명까지 보호할 수 없음을 확인했음

### 2. 최소 수정

**사용자 요청**

- 확인된 문제 해결 요청

**결과**

- JSON 검증과 값 변환 이후 기존 mutex를 획득하도록 수정했음
- 잠금 범위에서 클라이언트를 조회하고 존재하는 경우에만 상태 갱신
- 서버 빌드 성공 및 diff 공백 검사 통과

## 조언

- 공유 값의 동기화와 해당 값을 소유한 객체의 수명 보호를 함께 검토할 필요
- 기존 mutex를 활용하면 atomic 도입에 따른 객체 복사 방식 변경 없이 최소 수정 가능

| `docs/solve-log/2026-11-18-boost-status-race.md` | 분석 근거와 해결 및 검증 결과를 기록했다. |

## 확인 결과

- `server/`에서 CMake 구성 후 `make -j2` 실행, 전체 서버 컴파일과 링크 성공
- `git diff --check` 통과
- 코드 검토: true/false 모두 기존 JSON 검증 후 동일한 잠금 경로로 갱신
- 코드 검토: 클라이언트 삭제가 먼저 완료된 경우 조회 실패로 반환하고 항목을 생성하지 않음
- 코드 검토: 핸들러 호출 시 상위 읽기 경로의 잠금이 해제되어 있어 추가 잠금의 중첩 없음
- 실제 네트워크 부하 환경과 ThreadSanitizer를 이용한 수정 전후 재현은 수행하지 않았음
- 다른 핸들러의 잠금 없는 컨테이너 접근은 이번 수정 범위에서 제외했음
