# [중요] boost_status 데이터 경합 해결

## 문제 요약

네트워크 스레드는 일반 bool인 `boost_status`를 잠금 없이 변경하고 게임 스레드는
mutex를 보유한 상태에서 읽어, 두 접근 사이의 동기화가 보장되지 않았다.

### 문제 발생 조건

- 코드 확인: 네트워크 스레드의 부스트 메시지 처리와 게임 스레드의 이동 처리 병행
- 코드 확인: 메시지 추출의 잠금 해제 후 부스트 핸들러 호출
- 실제 플레이 중 오동작이나 충돌 증상은 직접 재현하지 않았음

## 원인 및 해결

읽는 쪽만 mutex를 사용해 쓰기와 읽기가 상호 배제되지 않았다. 쓰기 경로에서도
기존 `server_mutex`를 잡고 클라이언트 조회와 상태 갱신을 수행하도록 변경했다.
삭제된 클라이언트는 무시하며, `operator[]`에 의한 항목 재생성도 방지했다.

## 문제 상세

### 이전 값으로 한 틱 처리해도 되는데 왜 문제인가

게임 규칙만 보면 게임 스레드가 부스트 값을 읽기 전에 입력이 반영되면,
이번 틱부터 읽은 후에 반영되면 다음 틱부터 적용해도 된다.
문제는 이 반영 시점의 차이가 아니라, 일반 `bool`을 동기화 없이 공유했을 때
C++이 그런 식의 읽기와 쓰기를 보장하지 않는다는 점이다.

일반 변수에서 한 스레드의 쓰기와 다른 스레드의 읽기 사이에 필요한 순서 관계가
없으면 데이터 경합이 된다. 이때 C++은 동작을 보장하지 않는다. 정확히 같은
CPU 사이클에 접근해야만 문제가 되는 것도 아니다. 실제 시간상 먼저 실행됐다는
사실만으로 스레드 사이의 동기화 관계가 생기지는 않는다.

### 가시성과 CPU 파이프라인의 관계

메모리 가시성은 한 스레드가 변경한 값을 다른 스레드가 어떻게 관찰하는지에
관한 개념이다. CPU의 명령 실행 순서, 쓰기 버퍼와 캐시뿐 아니라 컴파일러의
최적화까지 관련되므로, 이 문제를 CPU 파이프라인 문제만으로 부르면 범위가 좁다.

컴파일러는 정의된 동작을 하는 프로그램에 데이터 경합이 없다는 전제에서
최적화할 수 있다. 따라서 소스 코드에 일반 변수 읽기가 있다는 사실만으로
매번 다른 스레드의 변경을 반영하는 메모리 읽기가 수행된다고 가정할 수 없다.
값을 레지스터에 보관하거나 이미 읽은 값을 재사용하는 것이 개념적인 예다.
현재 서버에서 실제로 그러한 최적화가 발생했음을 측정한 것은 아니다.

이 문제의 정확한 분류는 **데이터 경합**이다. 가시성은 관련 개념이며,
이번 장애의 원인이 특정 CPU의 캐시나 파이프라인이었다고 확인한 것은 아니다.
`bool` 접근이 특정 CPU에서 한 명령으로 처리되더라도 C++의 동기화 보장이
자동으로 생기지는 않는다.

### 우리 코드에서 보호가 끊긴 위치

`ClientContext::boost_status`는 atomic이 아닌 일반 `bool`이었다.
각 접근의 실제 범위는 다음과 같았다.

| 실행 경로 | 접근과 잠금 범위 |
|---|---|
| 네트워크 스레드의 `Server::handle_read` | `server_mutex`를 잡고 메시지 추출 후 블록을 벗어나 잠금 해제 |
| 이후 `handle_message` → `handle_boost_status` | mutex 없이 `client_contexts[id].boost_status`에 대입 |
| 게임 스레드의 `game_loop` | `server_mutex`를 잡고 `client.boost_status`를 읽어 이동 속도 결정 |

메시지 추출 때 사용한 잠금은 이후 핸들러의 대입까지 보호하지 않았다.
게임 스레드가 잠금을 보유해도 네트워크 스레드가 같은 잠금을 획득하지 않고
대입하므로 두 접근이 서로를 기다리지 않았다. mutex는 변수에 자동으로 붙는
보호 장치가 아니라, 같은 mutex를 사용하는 코드 구간끼리 접근을 조율하는 장치다.

가능한 상황을 단순화하면 다음과 같다.

```text
게임 스레드:     server_mutex 획득 → boost_status 읽기 → 잠금 해제
네트워크 스레드:                    boost_status 쓰기
                                   ↑ 같은 mutex를 사용하지 않음
```

이전 값 또는 새 값 중 하나로 정상 처리됐다는 관찰만으로는 경합이 없다는 결론을
낼 수 없다. 실행 증상이 드러나지 않아도 소스 코드의 동기화 보장은 빠져 있었다.

### 수정이 보장하는 것

수정 후 `handle_boost_status`는 JSON 검증과 값 변환을 마친 뒤
`server_mutex`를 획득한다. 잠금 안에서 클라이언트를 찾고 존재할 때만 값을 쓴다.
이제 게임 스레드의 읽기와 네트워크 스레드의 쓰기는 같은 mutex로 상호 배제된다.

쓰기 후 잠금을 해제하고 게임 스레드가 같은 mutex를 획득하면,
앞선 쓰기와 이후 읽기 사이에 C++의 happens-before 관계가 형성된다.
이는 스레드 사이에서 앞선 작업의 결과를 이후 작업이 관찰할 수 있도록 보장하는
순서 관계다. 단순히 동시에 접근하지 못하게 하는 역할에 더해 메모리 가시성도
보장한다. 반대로 게임 스레드가 먼저 잠갔다면 그 틱은 이전 값으로 처리되고,
네트워크 스레드의 갱신은 잠금 해제 이후 진행된다. 이는 허용된 게임 동작이다.

객체 수명도 함께 고려했다. 게임 스레드의 사망 처리는 같은 mutex 안에서
`disconnect_client_locked`를 호출해 `client_contexts`의 항목을 삭제할 수 있다.
따라서 잠금 없이 컨테이너를 조회하거나 삭제된 객체에 접근하는 문제도 피해야 한다.
잠금 안의 `find`가 실패하면 반환하므로 이미 삭제된 항목을 다시 만들지 않는다.
기존 `operator[]`는 항목이 없으면 새 `ClientContext`를 생성할 수 있었다.

### atomic과 mutex를 선택하는 기준

독립적인 bool 하나의 전달만 필요하고 그 객체의 수명이 별도로 보장된다면,
양쪽 접근을 `std::atomic<bool>`의 `store`와 `load`로 처리할 수 있다.
다른 데이터의 공개 순서까지 보장할 필요가 없다면 `memory_order_relaxed`도
후보가 된다. 다만 이 방식은 다른 변수의 가시성이나 컨테이너의 안전성까지
보장하지 않으며, 어느 틱에 반영될지 정해 주는 도구도 아니다.

우리 코드에서는 클라이언트 조회·삭제와 상태 갱신을 함께 보호해야 하므로
기존 mutex를 활용했다. `volatile`은 C++ 스레드 사이의 동기화를 제공하지 않아
이 문제의 해결 수단이 아니다.

복기할 핵심은 **“한 틱 늦어도 괜찮다”는 게임 요구와 “동기화 없이 공유해도
괜찮다”는 메모리 접근 조건은 서로 다르다**는 점이다.
