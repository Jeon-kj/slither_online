# 잘못된 메시지 길이로 인한 연결별 수신 처리 정체 해결

## 문제 요약

잘못된 본문 길이를 수신하면 해당 연결의 이후 정상 메시지도 처리되지 않고 수신 버퍼가 증가했다.

### 문제 발생 조건

- 수정 전 서버 소스와 로컬 소켓으로 실제 수신·추출·처리 함수를 실행해 직접 확인
- 본문 길이가 음수 또는 10,000 초과인 헤더 전송 후 같은 연결로 정상 메시지 추가 전송
- 연결은 유지되지만 정상 메시지는 처리되지 않고 버퍼와 오류 로그가 증가했음
- 현재 Unity 클라이언트의 일반 플레이에서 해당 길이가 발생하는 경로는 확인하지 못했음

## 원인 및 해결

`extract_message`가 추가 수신 필요와 잘못된 메시지를 모두 `false`로 반환하고,
잘못된 헤더를 버퍼에 남겼다. 이후 수신에서도 같은 헤더를 검사해 메시지 처리가 정체됐다.
추출 결과를 완료·추가 수신 필요·잘못된 메시지로 구분하고, 잘못된 메시지는 기존 연결 정리
함수로 종료하도록 변경했다. 추가 수신이 필요한 경우는 버퍼를 보존한다.

## 해결 과정

### 1. 재현과 운영 발생 가능성 검토

**사용자 요청**

- 잘못된 길이 수신 후 메시지 처리 정체 재현 및 운영 중 발생 가능성 검증 요청
- 해결 방법과 본문 길이 10,001바이트의 처리 기준 설명 요청

**결과**

- 길이 -1과 10,001 전송 후 정상 부스트 메시지 101개가 처리되지 않고 버퍼가 2,836바이트로 증가함을 확인했음
- 정상 분할 수신과 다른 연결의 메시지 처리는 동작함을 확인했음
- Unity 송신부가 실제 본문 바이트 수로 길이를 기록하며 채팅 UI 연결은 주석 처리돼 있음을 확인했음
- 비정상 클라이언트가 직접 접속하는 경우 발생 가능한 입력 처리 결함으로 판단했음
- 선언된 본문 길이 10,001은 즉시 거부하며, 허용 길이의 본문이 덜 도착한 경우만 추가 수신을 기다리도록 제시했음

### 2. 결과 구분과 연결 종료 적용

**사용자 요청**

- 권장 처리 방법에 따른 코드 수정 요청

**결과**

- `ExtractResult`로 완료·추가 수신 필요·잘못된 메시지 구분을 적용했음
- 잘못된 메시지는 잠금을 보유한 위치에서 `disconnect_client_locked` 호출 후 수신 함수에서 즉시 반환하도록 변경했음
- 추가 수신 필요는 기존처럼 추출 반복만 중단하고 수신 버퍼를 보존하도록 유지했음

## 조언

- 수신 데이터 전체 크기가 아닌 각 메시지의 선언된 본문 길이를 제한 기준으로 유지할 필요
- 허용 길이를 선언한 뒤 본문을 완성하지 않는 연결의 시간 제한은 별도 요구사항으로 판단할 필요

## 변경 파일

| 파일 | 변경 내용 |
|---|---|
| `server/message_handler.hpp` | 추출 함수의 bool 결과를 세 가지 상태의 열거형으로 변경했다. |
| `server/message_handler.cpp` | 부족한 데이터와 유효하지 않은 길이의 반환 결과를 구분했다. |
| `server/server.cpp` | 잘못된 길이의 연결을 정리하고 즉시 반환하도록 변경했다. |

## 확인 결과

- 수정 전후 동일한 로컬 소켓 기반 검증에서 실제 서버 수신·추출·처리 함수를 실행했음
- 수정 후 길이 -1과 10,001에서 연결 종료 및 컨텍스트·매핑·연결 목록 정리를 확인했음
- 잘못된 헤더 뒤에 붙은 정상 메시지가 처리되지 않고 연결이 종료됨을 확인했음
- 헤더와 본문을 각각 나누어 보낸 경우 버퍼 보존 후 메시지 처리 성공
- 잘못된 연결 종료 후 다른 연결의 정상 메시지 처리 성공
- 여러 정상 메시지를 붙여 보낸 경우 순차 처리 성공
- 본문 10,000바이트인 전체 10,008바이트 메시지가 여러 recv 호출에 걸쳐 정상 추출됨을 확인했음
- 본문 길이 0과 10,000의 추출 성공
- `server/`에서 `make` 실행은 Makefile 부재로 실패했으며, 기존 빌드 디렉터리의 `cmake --build server/build -j2` 성공
- `git diff --check` 통과
- Unity 플레이 및 전체 epoll·게임 루프를 함께 실행한 검증은 수행하지 않았음
- 추가 수신 대기의 시간 제한과 클라이언트 송신 길이 제한은 이번 수정에 포함하지 않았음
- 사용자 환경에서의 해결 여부는 아직 확인받지 않았음
