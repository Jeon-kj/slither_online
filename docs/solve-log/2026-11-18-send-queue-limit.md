# 느린 클라이언트의 송신 대기열 누적 제한

## 문제 요약

클라이언트가 충분히 읽지 않으면 서버의 송신 대기열이 제한 없이 증가할 수 있었다.

### 문제 발생 조건

- 분석 기준 커밋 `3299ef3`의 비차단 TCP 서버
- 코드 분석으로 확인한 조건: 연결 유지 중 메시지 생성 속도가 송신 속도를 지속적으로 초과하는 경우
- 사용자 제기 사항: 보내지 못한 데이터가 계속 쌓일 가능성과 수정 필요성
- 수정 후 직접 검증한 조건: 로컬 TCP 클라이언트 3개 중 2개의 읽기를 중단하고, 나머지 1개에서 메시지를 전송·수신하는 경우
- 수정 전 실행 재현은 수행하지 않았으며, 무제한 적재 경로는 코드로 확인

## 원인 및 해결

`utils::send_queue()`가 제한 없이 패킷을 추가하고, `EAGAIN` 발생 시에는 송신만
대기하므로 이후 생성되는 메시지가 누적되는 구조였다. 클라이언트별 미송신 바이트에
헤더를 포함한 1 MiB 상한을 적용했다. 상한 초과 패킷은 적재하지 않고 이후 적재도
중단하며, 게임 틱 끝에서 해당 연결을 종료하고 남은 클라이언트에 퇴장을 알린다.
부분 송신과 전체 송신 시 실제 송신 바이트만큼 대기량을 차감한다.

## 해결 과정

### 1. 발생 가능성과 해결책 분석

**사용자 요청**

- 별도 worktree 생성 및 송신 대기열 누적의 발생 가능성·심각도·수정 필요성 분석 요청
- 코드 수정 없이 해결책 제시 요청

**결과**

- `review/send-backpressure` 브랜치의 worktree 생성
- 무제한 큐 적재와 송신 정체 시 추가 적재 지속 경로 확인
- 메모리 부족 위험 확인 및 공용 락 대기에 따른 게임 지연 가능성 제시
- 대기 바이트 상한과 오래된 메시지 대기 시간 제한을 초기 해결책으로 제안했음

**사용자 후속 요청**

- 시간 제한의 필요성 재검토 및 용량 제한만으로 해결 가능한지 확인 요청

**결과**

- 메모리 누적 방지에는 바이트 상한으로 충분하며 시간 제한은 추가 방어책으로 정리했음
- 클라이언트별 수신 속도는 다를 수 있으므로 오래된 데이터 누적 가능성 자체는 남음을 설명했음

### 2. 바이트 상한 적용 및 검증

**사용자 요청**

- 합의한 송신 큐 바이트 상한 적용 요청

**결과**

- 기존 `GameConfig`에 클라이언트별 1 MiB 상한 추가
- 패킷 생성 전 헤더 포함 대기량 검사와 상한 초과 후 추가 적재 차단 적용
- 부분·전체 송신 시 바이트 차감 적용
- 순회 중 삭제를 피하도록 게임 틱 끝에서 초과 연결을 먼저 정리한 뒤 퇴장을 알리는 순서 추가
- 빌드, 바이트 경계 검사 및 실제 TCP 연결 종료·정상 수신 검증 통과

## 조언

- 메모리 누적이라는 목표에는 용량 제한을 먼저 적용하고, 지연 시간 보장 요구가 생겼을 때 시간 제한 검토 권장
- 위치 메시지가 클라이언트 몸통 경로의 입력이므로, 최신 위치만 남기는 최적화는 별도 동작 검증 필요

| `server/server.cpp` | 송신 시 대기량을 차감하고 게임 틱 끝에서 초과 연결 정리와 퇴장 알림을 수행하도록 변경했다. |
| `docs/solve-log/2026-11-18-send-queue-limit.md` | 분석·정책 결정·수정 및 검증 결과를 기록했다. |

## 확인 결과

- CMake로 Makefile 생성 후 `server/`에서 `make -j2` 빌드 통과
- 소켓 기반 경계 검사: 정확히 상한까지 적재 허용, 초과 적재 거부, 단일 초과 패킷 거부, 반복 적재 차단 확인
- 부분 송신 시 대기량 차감, `EAGAIN` 시 대기량 유지, 전체 송신 후 대기량 0 및 `EPOLLOUT` 해제 확인
- 존재하지 않는 fd로 적재 시 클라이언트 상태를 새로 만들지 않음 확인
- 실제 TCP 검증: 읽기를 중단한 클라이언트 2개 종료, 정상 클라이언트의 퇴장 알림 2개 수신 및 이후 메시지 수신 확인
- `git diff --check` 통과
- 1 MiB는 초기 정책값이며 실제 운영 트래픽에 따른 적정 상한은 미측정
- 상한은 애플리케이션 큐의 미송신 데이터 기준이며, 컨테이너·할당 여유 공간과 커널 소켓 버퍼를 포함한 프로세스 전체 메모리 상한은 아님
- Unity 화면과 실제 운영 환경의 장시간 검증은 수행하지 않았음
- 클라이언트 수신 큐 제한은 별도 문제로 남았으며 이번 변경 범위에서 제외
