# 클라이언트 증가 시 서버 감속과 위치 JSON 중복 생성 개선

## 문제 요약

봇 접속 수가 50명을 넘으면서 최초 접속 클라이언트에서 이동이 느려지고, 봇이 모두
종료되면 정상 속도로 돌아온다는 사용자 보고. 로컬 TCP 부하 시험에서도 위치 수신
간격 증가와 실제 서버 좌표 진행 속도 감소를 확인했음.

### 문제 발생 조건

- 사용자 보고: 서버 실행 후 Unity 클라이언트에서 관찰하며
  `dotnet run --project bot_client -- --host 127.0.0.1 --port 12345 --bots 100 --spawn-rate 5` 실행
- 사용자 보고: 봇 50명 초과 시 감속 심화, 봇 종료 시 회복
- 직접 확인: 현재 최적화 옵션 없는 CMake 빌드에 로컬 TCP 연결 1·25·50·100개를 생성하면 부하 증가에 따라 감속 발생
- 봇의 방향 입력, 장시간 몸통 성장, Unity 렌더링이 필수 발생 조건인지는 미확인

## 원인 및 해결

게임 루프가 수신자마다 전체 위치 JSON을 다시 생성·직렬화하여 틱당 작업이 O(N²)로
증가했음. 틱마다 위치 JSON을 한 번 생성하고, 같은 본문을 입장 완료된 모든 연결의
송신 큐에 넣도록 변경했음. JSON 파일을 디스크에 저장하는 방식이 아닌, 메모리의
직렬화된 JSON 문자열 재사용 방식.

게임 처리가 끝난 뒤 항상 20ms를 쉬면서 게임 시간은 틱당 20ms만 진행하는 구조가
처리 지연을 실제 이동 감속으로 연결했음. 1차 수정에서는 JSON 중복 생성만 제거했고,
2차 수정에서는 단조 시계의 다음 틱 예정 시각까지 남은 시간만 대기하도록 변경했음.
처리가 예정 시각을 넘으면 기준을 현재 시각으로 재설정해 무제한 따라잡기를 방지했음.
넓은 락과 관심 영역 등은 후속 후보로 유지했음.

## 해결 과정

### 1. 원인 분석과 부하 확인

**사용자 요청**

- 클라이언트 증가에 따른 감속의 정확한 원인 분석 및 해결 우선순위 정리 요청
- 전체 브로드캐스트, 넓은 락, 두 스레드 구조를 원인 후보로 제시했음

**결과**

- 수신자별 전체 위치 JSON 생성·직렬화 반복과 처리 후 고정 대기를 확인했음
- 초기 분석의 수정 전 시험에서 연결 1개 대비 100개일 때 수신 간격 약 20ms → 109ms, 이동 속도 약 1.284 → 0.238 units/s 확인
- 임시 계측 서버의 20틱 평균에서 약 98명 시 위치 생성·송신 큐 등록 88.13ms, 충돌 검사·결과 반영 1.67ms 확인
- 해당 계측 조건에서 위치 전송 준비를 주 병목으로 판단했음
- 같은 전역 락을 사용하는 게임·네트워크 처리의 상호 대기 가능성 확인, 락 대기 시간 자체는 별도 미측정

### 2. 위치 JSON 단일 생성 적용과 전후 비교

**사용자 요청**

- 개선안을 하나씩 적용하고 전후 기록을 비교하도록 요청
- 전체 위치 JSON을 한 번 생성해 전체 클라이언트에게 보내는 1번 해결안만 적용하도록 요청
- 나머지 개선 방법은 solve-log에 기록만 하도록 요청

**결과**

- 게임 루프의 수신자별 `send_pos(fd, ctx)` 호출을 틱당 `send_pos(ctx)` 한 번으로 변경했음
- `send_pos`에서 전체 위치를 한 번 수집·직렬화하고 같은 본문을 모든 활성 수신자에게 등록하도록 변경했음
- 이동·경계 사망 처리 뒤, 충돌 검사 앞이라는 기존 위치 전송 시점 유지
- 입장 완료 전 연결은 수신자에서 제외하고 전체 위치 본문에는 포함하는 기존 조건 유지
- 동일 부하 스크립트의 수정 직전·직후 측정에서 100개 연결의 평균 수신 간격 103.05ms → 26.65ms, 이동 속도 0.252 → 0.976 units/s 확인
- 기존 빌드 및 동일 본문·활성 수신자·빈 수신자 검증 통과, Unity 화면의 실제 체감 개선은 사용자 확인 대기

### 3. 틱 스케줄 수정과 트레이드오프 확인

**사용자 요청**

- 틱 스케줄 수정 후 구현 방식과 잃은 것·트레이드오프를 과장 없이 보고하도록 요청

**결과**

- `steady_clock` 기준의 다음 예정 시각을 `DELTA_TIME` 간격으로 증가시키고 `sleep_until`로 남은 시간만 대기하도록 변경했음
- 기존 이동·면역·부스트의 고정 20ms 스텝과 게임 상태 처리 순서 유지
- 처리·락 대기 등이 다음 예정 시각을 넘으면 기준 시각 재설정, 밀린 틱의 무제한 따라잡기 제외
- 동일 부하의 수정 직전·직후 시험에서 100개 연결의 평균 수신 간격 27.31ms → 20.03ms, 이동 속도 0.952 → 1.298 units/s 확인
- 100개 연결에서 CPU 44.60% → 50.16%, 총 수신량 23.42 → 31.33 MB/s 증가 확인
- 프로세스 일시 정지·재개 후 누적 틱의 대량 실행 없이 주기 회복 확인

## 조언

- 한 번에 한 변경을 적용하는 비교 방식 유지 권장. 다음 단계에서도 현재 결과를 기준으로 같은 환경·부하로 비교할 필요
- 두 스레드라는 개수만으로 병목을 판단하기보다 직렬화 비용, 공유 락 대기, 큐 적체를 각각 계측할 필요
- 이번 수정 후 틱 실행 빈도가 늘면서 총 수신량도 증가했으므로 CPU 감소와 전송량 감소를 같은 효과로 해석하지 않을 필요

### 후속 개선 후보 — 틱 예약 외 미적용

1. **시뮬레이션·전송 주기 분리 및 과부하 정책:** 고정 시간 기준 틱 예약은 2차 수정에서 적용했음. 별도 전송 주기와 누적 시간 기반 따라잡기는 미적용. 지속적으로 틱 처리가 20ms를 초과하면 감속이 남으므로 처리량 개선 또는 별도 과부하 정책 검토 필요.
2. **게임 상태와 네트워크 락 분리:** 게임 스레드의 상태 소유 및 입력·출력 큐 도입 후보. 우선 짧은 락 안에서 스냅샷을 추출하고 직렬화를 밖으로 옮기는 단계적 접근 가능. 락 대기 감소 효과는 미측정 가설.
3. **관심 영역(AOI) 적용:** 주변 객체와 관련 이벤트만 전송하여 전체 브로드캐스트의 전송량과 클라이언트 처리량을 축소하는 후보. 시야 진입·이탈·재진입 시 상태 동기화 및 프로토콜 결정 필요.
4. **송신 적체 및 클라이언트 처리 제한:** 큐 크기·대기 시간 계측, 오래된 위치와 필수 이벤트의 처리 정책 분리, 프레임별 작업량 관리 후보. 수신 위치로 몸통 경로를 구성하는 현재 클라이언트에서 위치를 단순 폐기하면 경로 변화 가능. 적체와 Unity GC·프레임 시간은 미측정.
5. **충돌 공간 분할:** 머리·몸통·먹이의 전체 순회를 공간 격자의 근거리 후보 검사로 변경하는 후보. 이번 짧은 시험에서는 위치 준비보다 비용이 작았으며, 긴 몸통·장시간 부하에서는 재평가 필요.
6. **Release 최적화 빌드 비교:** 현재 빌드에 없는 최적화 옵션 적용 후보. 중복 계산과 틱 스케줄 문제는 별도이며 효과는 미측정.
7. **완성 패킷 공유:** 이번에는 JSON 본문만 재사용하며 `utils::send_queue`의 연결별 패킷 생성·복사는 유지. 불변 패킷과 연결별 전송 오프셋 분리 후보, 효과는 미측정.

## 확인 결과

### 1차 수정: JSON 단일 생성 직전·직후 측정

| 생성 연결 수 | 연결 수 중앙값 전 → 후 | 평균 수신 간격 전 → 후 | 수신 간격 p95 전 → 후 | 이동 속도 전 → 후 | 서버 CPU 전 → 후 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 → 1 | 20.22 → 20.23ms | 20.34 → 20.36ms | 1.286 → 1.285 units/s | 1.00 → 1.20% |
| 25 | 23 → 23 | 25.48 → 21.41ms | 41.68 → 21.91ms | 1.020 → 1.214 units/s | 24.76 → 9.78% |
| 50 | 48 → 48 | 41.85 → 23.01ms | 43.50 → 23.82ms | 0.621 → 1.130 units/s | 58.12 → 19.80% |
| 100 | 100 → 98 | 103.05 → 26.65ms | 108.91 → 29.85ms | 0.252 → 0.976 units/s | 89.63 → 39.34% |

- 환경: WSL2 Linux x86_64, AMD Ryzen 5 7600, 기존 CMake 빌드의 최적화 옵션 없음
- 동일 스크립트·동일 빌드 설정으로 전후 각 1회 실행. 각 연결 수에서 서버를 새로 실행하고 로컬 TCP 연결을 일괄 생성하여 5초간 수신
- 위치 통계는 최초 1초 제외 후 관찰 후보 3개 중 표본 수가 가장 많은 연결에서 산출. 이동 속도는 관찰 구간 양끝에 모두 존재하는 객체의 직선 변위/실제 경과 시간 중앙값
- 기본 이동 속도 설정 1.3 units/s. CPU는 프로세스 CPU 시간/실제 경과 시간이며 100%는 논리 CPU 하나 사용에 해당. CPU·총 수신량은 5초 전체 구간 기준
- 같은 수의 연결을 투입했으나 게임 진행이 빨라지며 사망 시점이 달라져 실제 생존 연결 수는 전후 완전히 같지 않음
- 총 수신량은 100개 연결에서 6.88 → 24.43 MB/s로 증가. 위치 갱신 빈도 회복에 따른 결과이며 바이트 수 절감은 이번 수정의 효과가 아님
- `bot_client`와 `dotnet`을 찾지 못해 지정 명령 대신 기존 분석에서 사용한 Python TCP 부하 스크립트 재사용. 방향 입력·5명/초 입장·Unity 화면·장시간 성장은 미검증
- 실행 명령: `python3 /tmp/slither-load-analysis.py` (12345 포트 사용, 실행 시점의 `server/build/MyServer` 측정)
- 재사용 스크립트 사본: `/tmp/slither-json-once/probe.py`
- 원본 결과: `/tmp/slither-json-once/before/results.json`, `/tmp/slither-json-once/after/results.json`
- 서버 원본 로그: 위 `before/`, `after/` 각각의 `slither-analysis-server-{1,25,50,100}.log`. 임시 경로이므로 환경 정리 시 소실 가능
- 수정 전 기준 커밋: `df2f5575157ccb048752e098e465472e8283e733`, 수정 전 작업 트리 변경 없음

- 임시 검증 프로그램 `/tmp/slither-json-once/check` 실행 통과: 두 활성 수신자의 JSON 본문 일치, `MSG_POS` 타입 및 기존 필드 유지, 비활성 연결의 수신 제외·본문 포함, 빈 연결 및 활성 수신자 없는 경우 송신 없음

- 수정 직전 서버 소스 사본: `/tmp/slither-tick-schedule/server-before.cpp`. 임시 측정 경로는 환경 정리 시 소실 가능
- 총 수신량 100개 연결에서 23.42 → 31.33 MB/s 증가. CPU 증가는 초당 틱·전송 횟수 회복과 함께 관찰됐으며 모든 연결 수에서 일관된 증가는 아니었음
- 각 수신 간격을 정확히 20ms로 보장하는 변경은 아님. 25개 연결의 p95 약 41ms 등 수신 변동 잔존, 구체적 원인은 이번에 분리 계측하지 않았음
- `bot_client` 방향 입력·5명/초 입장·Unity 화면·장시간 부하 미검증이라는 1차 시험의 한계 유지

### 2차 수정 빌드·경계 동작 및 트레이드오프

- `server/`에서 `make -C build -j 2` 실행, `MyServer` 빌드 통과
- `python3 /tmp/slither-tick-schedule/pause-check.py` 실행, 별도 서버를 약 330ms 정지 후 재개했을 때 첫 120ms에 7회, 다음 200ms에 10회 위치 수신 확인. 원본 결과 `/tmp/slither-tick-schedule/pause-result.json`
- 정상 부하에서 틱당 처리 비용을 줄인 변경이 아니라 초당 실행 횟수를 약 50회로 회복한 변경. CPU·네트워크·클라이언트의 초당 처리량 증가 가능, 서버 CPU·수신량 증가는 100개 연결 시험에서 직접 확인
- 한 틱이 계속 20ms를 초과하면 대기 시간을 없애도 실제 게임 시간이 느려질 수 있음. 장시간 정지 때 잃은 게임 시간을 전부 복구하지 않는 정책으로, 과거 시점의 틱을 몰아서 처리하는 부담과 교환
- 초과 직후 다음 틱이 바로 실행되어 한 쌍의 위치 메시지가 가까워질 수 있으나, 누적된 틱을 계속 실행하는 반복 따라잡기는 없음
- 이동 스텝·충돌 판정·게임 상태 처리 순서는 유지. 락 밖의 마지막 대기 방식만 변경했으며 네트워크 메시지 형식 변경 없음
