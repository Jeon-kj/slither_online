# 봇 일괄 종료 시 SIGPIPE에 의한 서버 종료

## 문제 요약

다수 봇의 연결 종료 시 서버 프로세스까지 간헐적으로 종료되는 문제.

### 문제 발생 조건

- 사용자 보고: 서버 실행 후 `dotnet run --project bot_client -- --host 127.0.0.1 --port 12345 --bots 20 --spawn-rate 5` 실행 및 Ctrl+C 종료 시 발생. Unity 클라이언트 종료와 봇 1개에서는 미관찰.
- 직접 확인: WSL Linux 서버와 Windows .NET 10의 기존 봇 사용. 20개 봇, 초당 5개 접속, `--duration 8`을 통한 일괄 취소 2회 중 두 번째에서 서버 종료.
- `--duration`과 Ctrl+C는 동일한 CancellationTokenSource를 취소하고 기존 봇의 퇴장 패킷 전송·소켓 해제 경로를 실행하는 조건.

## 원인 및 해결

`Server::handle_write_locked()`의 `send(..., 0)`에서 끊긴 연결에 퇴장 알림을 전송하면서 EPIPE 및 SIGPIPE 발생. 시그널 기본 동작으로 서버 전체 종료. mutex는 상대방의 연결 종료를 막지 못하므로 잠금 추가로 해결되는 문제가 아님.

`send()`에 MSG_NOSIGNAL을 적용하여 해당 호출의 SIGPIPE만 억제. EPIPE는 그대로 반환되어 기존 `disconnect_client_locked()`로 연결 정리. 게임 규칙, 프로토콜, 잠금 및 호출 순서 변경 없음.

## 해결 과정

### 1. 분석 요청과 원인 가설

**사용자 요청**

- 봇 20개를 Ctrl+C로 종료할 때 서버도 종료되는 증상 전달
- Unity 클라이언트 종료와 봇 1개에서는 미관찰이라는 비교 조건 전달
- 멀티스레드 종료 처리 문제 가능성 제시 및 코드 수정 없이 원인 분석·보고 요청

**결과**

- 전송 오류 처리 분기보다 먼저 SIGPIPE로 프로세스가 종료될 가능성 확인.
- 네트워크 전송과 연결 정리, 게임 갱신에서 공통 mutex 사용 확인.
- 실제 종료 시그널을 포착하기 전이므로 SIGPIPE를 원인 가설로 보고했음

### 2. 기존 봇 재현·수정·재시험

**사용자 요청**

- 클라이언트 위치에서 bot_client를 찾아 오류를 재현하도록 요청
- 수정 후 재시험 및 트레이드오프 보고 요청

**결과**

- 클라이언트 저장소 루트의 `bot_client` 확인 및 기존 Windows .NET 실행 환경 사용.
- strace에서 퇴장 알림 전송의 EPIPE 직후 SIGPIPE 및 서버 전체 스레드 종료 확인.
- 전송 플래그만 MSG_NOSIGNAL로 변경.
- 수정 후 EPIPE가 발생해도 서버가 유지됨을 확인했음

### 3. 트레이드오프 설명 재검토

**사용자 요청**

- SIGPIPE 통지가 사라진다는 설명이 과장인지 및 현재 통지 활용 코드가 있는지 확인 요청

**결과**

- 현재 SIGPIPE를 활용하는 처리 코드가 없고 EPIPE 반환은 유지됨을 확인했음
- 통지 상실을 실질적 트레이드오프로 설명한 표현이 과했음을 인정했음
- 현재 구현에서 실질적 기능 손실은 없으며 미지원 플랫폼 이식 제약과 구분하여 정정했음

## 조언

- 간헐적 종료는 로그만으로 추정하지 않고 종료 시그널과 실패한 시스템 호출을 함께 확인하는 방식 권장.
- 프로세스 전체에서 SIGPIPE를 무시하는 설정보다 필요한 전송 호출에만 적용하는 방식 선택. 향후 다른 전송 호출을 추가하면 동일한 방어 필요.

## 확인 결과

- 수정 전: `sendto(..., 0) = -1 EPIPE` 직후 SIGPIPE 및 전체 스레드 종료 확인.
- 수정 후: `sendto(..., MSG_NOSIGNAL) = -1 EPIPE` 2회, SIGPIPE 발생 없음. 모든 시험 종료 후 서버 LISTEN 유지 및 남은 클라이언트 연결 없음 확인.
- `server/`에서 `make` 실행은 Makefile 부재로 실패. 기존 CMake 빌드 디렉터리를 사용하는 `make -C build -j2` 성공. `git diff --check` 통과.
- 실제 Ctrl+C 수정 후 시험 1회와 자동 취소 반복 시험 10회 통과. 수정 전 종료 원인 포착은 자동 취소 경로에서 수행했으며, 수정 전 실제 Ctrl+C 종료 재현은 미확인.
- WSL 콘솔의 Ctrl+C 입력 전달 및 상속된 Ctrl+C 무시 상태로 인한 초기 시험 제약 확인. 실행 부모의 무시 상태 해제 후 Windows 콘솔 Ctrl+C 이벤트로 정상 종료 확인.
- 반복 종료 후 봇 1개 재접속·게임 참가·종료 확인.
- 현재 구현에서 실질적 기능 손실 없음. SIGPIPE 활용 코드는 없으며 EPIPE 오류 처리는 유지. 연결 단절 시 대기 메시지 폐기는 기존 동작. MSG_NOSIGNAL 미지원 플랫폼으로 이식할 때 대체 처리 필요. 현재 서버는 이미 Linux epoll 사용.
- 성능 변화는 측정하지 않았으며 개선 효과 주장 없음. Unity 클라이언트 실행 시험은 미수행.
