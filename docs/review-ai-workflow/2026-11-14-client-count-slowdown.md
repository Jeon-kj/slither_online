# 클라이언트 증가에 따른 감속 개선의 AI 활용 회고

## 전체 평가

분석·구현·반복 시험은 넓게 위임하면서 변경 순서와 결과 해석은 직접 통제한 활용이었다. 개선안을 하나씩 적용해 비교하도록 요청했고, 정상 실행 빈도 회복에 따른 자원 증가를 손해로 해석한 설명에도 이의를 제기했다. 실행을 맡겼다는 이유로 과도한 의존이라고 판단할 근거는 없다.

다음 개선 방향은 변경 전 수용 기준을 정하고, 대체 부하 시험의 결과와 원래 환경에서의 해결 확인을 구분하는 것이다. 이번 과정에서 확인된 강점은 실험 범위를 통제하고 수치를 목표 동작에 비춰 해석한 판단이다. 이를 다른 부하 조건에서도 반복할 수 있다면 차별성의 근거가 될 수 있지만, 이번 한 사례로 성능 분석·구현 역량 전체를 입증했다고 보기는 어렵다.

## 요청별 평가

### 1. 증상·재현 방법을 제시하고 원인 분석 요청

**사용자 요청**

- 최초 접속 클라이언트에서 봇 50명 초과 시 감속이 심해지고, 봇이 모두 종료되면 회복된다는 관찰 전달
- 100개 봇을 초당 5개씩 접속시키는 실행 명령 제공
- 전체 브로드캐스트·넓은 락·스레드 구성을 원인 후보로 제시하고 분석 및 해결 우선순위 요청

**평가**

관찰 대상, 부하 증가에 따른 변화, 부하 제거 후 회복, 재현 명령까지 제공해 조사 출발점이 충분했다. 서버 구조는 추정으로 제시했으므로 관찰과 원인 단정을 구분한 요청이었다. 코드 분석과 측정을 AI에게 맡긴 범위도 적절했다.

다만 AI는 지정한 봇 실행 환경을 찾지 못해 대체 TCP 부하를 사용했다. 이 시험은 서버 감속의 존재와 원인 분석을 뒷받침하지만, 원래 봇 입력과 Unity 화면의 증상까지 검증한 것은 아니다. 사용자가 대체 시험을 원래 환경의 해결 확인과 동일하게 받아들였는지는 확인되지 않는다.

**더 효율적인 활용**

처음부터 더 많은 재현 자료를 준비할 필요는 없었다. 대체 시험이라는 한계가 보고된 뒤에는 원래 명령과 실제 화면으로 최종 확인하면 결과 수용의 정확도를 높일 수 있다. 환경 차이와 검증 범위를 밝히는 일 자체는 AI가 수행해야 할 책임이다.

### 2. 개선안을 하나씩 적용하고 전후 비교 요청

**사용자 요청**

- 개선안을 하나씩 적용하면서 수정 전후 기록 비교 요청
- 전체 위치 JSON을 한 번 생성해 전체 클라이언트에게 전송하는 방법부터 적용하도록 지정
- 나머지 개선안은 solve-log에 기록만 하도록 범위 제한

**평가**

각 변경의 효과를 구분하기에 적절한 요청이었다. JSON 재사용과 틱 스케줄 수정을 나눴기 때문에 수신 간격 개선이 어느 변경에서 발생했는지 비교할 수 있었다. 나머지 후보를 기록으로 남긴 것도 필요 이상으로 구현 범위가 커지는 일을 막았다.

구현과 시험은 AI에게 맡겼지만 실험 순서와 적용 범위는 사용자가 정했다. 이는 실행 위임과 판단 개입이 함께 나타난 사례다. 다만 측정 방법과 구체적인 수용 기준은 주로 AI가 정했으며, 사용자가 측정 설계 전체를 검토했는지는 대화에서 확인되지 않는다.

**더 효율적인 활용**

다음에는 변경 전에 평균 수신 간격뿐 아니라 p95와 실제 이동 속도도 비교 기준으로 합의하면 판단력을 높일 수 있다. 사용자가 시험을 모두 설계할 필요는 없으며, AI가 제안한 지표가 실제 목표인 정상 속도와 화면 지연을 충분히 나타내는지 검토하면 된다.

### 3. 남은 개선안의 예상 효과와 필요성 비교 요청

**사용자 요청**

- 목표 수신 간격 20ms와 초과 시간 6.65ms를 구분해 결과 해석
- 남은 방법별 예상 감소 수신 간격으로 적용 필요성을 설명하도록 요청

**평가**

개선안 목록을 모두 구현하기보다 현재 남은 문제에 얼마나 기여할지 비교하려는 요청이었다. 목표 주기와 초과 시간을 구분한 점에서도 수치를 그대로 수용하지 않고 의미를 해석한 근거가 드러난다.

다만 6.65ms는 네트워크 지연만이 아니라 처리·락 대기·스케줄링 등이 합쳐진 초과 시간이다. 당시 여러 개선안의 예상 범위는 구간별 측정이 없어 넓거나 조건부였다. 이런 값은 우선순위 탐색에는 쓸 수 있지만 구현 효과의 보장값으로 수용할 근거는 부족했다.

**더 효율적인 활용**

예상 효과를 요청할 때 측정 근거가 있는 추정, 계산상 한계, 아직 산정할 수 없는 항목을 구분하도록 하면 정확도를 높일 수 있다. 예측이 어려운 항목은 숫자를 억지로 좁히기보다 다음에 측정할 구간을 정하는 근거로 활용하는 편이 효율적이다.

### 4. 틱 스케줄 구현·트레이드오프 보고와 해석 교정

**사용자 요청**

- 틱 스케줄 수정 후 구현 방식과 잃은 것·트레이드오프를 과장 없이 보고하도록 요청
- 수정 후 자원 사용 증가가 정상 실행 흐름에 필요한 비용이라는 점을 지적

**평가**

효과뿐 아니라 구현 방식과 변경 영향을 요구한 것은 충분했다. 이어서 정상적인 50Hz 실행에 필요한 자원 증가를 손해로 부를 수 있는지 검토한 점은 결과 수용 과정의 구체적인 개입이었다. CPU 사용량 감소를 무조건 개선으로 보는 대신 목표 동작과 연결해 해석했다는 근거다.

이 과정에서 확인된 것은 성능 수치에 대한 사용자의 판단이다. 병목 계측과 스케줄 구현 자체는 AI가 수행했으므로 그 작업을 사용자의 코드 구현 역량으로 귀속할 수는 없다. 또한 자원 증가 설명을 교정했다는 사실만으로 과부하 처리 정책까지 모두 이해했다고 판단하지 않는다.

**더 효율적인 활용**

현재 요청과 개입으로 충분했다. 트레이드오프를 반드시 찾아내도록 더 강하게 요구할 필요는 없다. 실제 회귀, 정상 처리량 회복에 필요한 비용, 기존부터 남아 있던 한계를 구분해 받아보면 불필요하게 단점을 부풀리지 않으면서 변경 영향을 판단할 수 있다.

## 결과 수용에 필요한 이해

**확인된 것**

- 증상과 원인 추측을 구분해 전달하고 재현 명령을 제공했음
- 개선안을 단계적으로 적용하고 전후 비교하도록 실행 범위를 통제했음
- 목표 주기 20ms와 관찰된 초과 시간을 구분해 해석했음
- 정상 실행 빈도 회복에 필요한 자원 증가와 성능 손해를 구분해 AI의 설명을 교정했음
- 구현 방식과 변경 영향에 대한 설명을 요구했음

**확인되지 않은 것**

- 초과 수신 간격이 순수 네트워크 지연과 다른 이유를 각 처리 구간에 연결해 설명할 수 있는지 여부
- `Server::main_loop()`의 `next_tick` 갱신과 초과 시 기준 시각 재설정이 장시간 정지·지속 과부하에서 어떤 동작을 만드는지 코드 수준에서 이해했는지 여부
- 고정 게임 시간 스텝 유지와 밀린 틱을 따라잡지 않는 정책의 차이를 이해했는지 여부
- 원래 봇 실행 명령과 Unity 화면에서 직접 재시험해 최종 해결을 확인했는지 여부

미확인을 이해 부족이나 무비판적 수용으로 단정할 수는 없다. 결과 수용에 필요한 추가 확인은 스케줄의 정상·초과 처리 경계와 원래 재현 환경의 동작에 집중하면 충분하다. 이번 회고만으로 분석·구현 역량 전체를 평가하지 않는다.

## 다음 작업에 적용할 원칙

**변경 전 성공 기준을 정하고, AI 측정 결과로 잠정 판단한 뒤 원래 재현 환경에서 최종 수용한다.**

사용자가 모든 코드를 직접 작성하거나 시험을 직접 설계할 필요는 없다. AI가 제안한 지표와 검증 범위가 실제 목표에 맞는지 확인하고, 대체 시험으로 남은 불확실성을 최종 판단에 반영하는 것이 핵심이다.

## 검토 범위

현재 대화의 클라이언트 증가에 따른 감속 분석, JSON 단일 생성 적용, 남은 개선안의 예상 효과 비교, 틱 스케줄 수정과 자원 사용 해석 교정을 검토했다. 근거는 사용자의 실제 요청·개입과 대화에 보고된 분석·측정 결과다. 이후 회고 스킬 실행 및 Markdown 저장 요청은 평가 범위에서 제외했다.

이번 회고에서는 코드를 수정하거나 서버 시험을 다시 실행하지 않았다. 원래 봇 실행 및 Unity 화면 검증은 확인되지 않았으며, 수치 개선 보고와 실제 사용자 환경의 해결 확인을 구분했다.
