# 송신 대기열 제한 작업의 AI 활용 회고

## 전체 평가

발생 가능성과 수정 필요성을 먼저 확인하고, 이해되지 않는 대책을 질문한 뒤
목표에 필요한 범위로 구현을 좁힌 활용 방식은 적절했다.
분석·구현·시험을 넓게 맡겼지만, 제안된 정책을 직접 검토한 행동이 있어
과도한 의존으로 판단할 근거는 없다.

개선할 지점은 해결책을 줄일 때의 근거와 구현 결과를 수용하는 기준이다.
“모두에게 비슷하게 보낸다”는 사실은 수신 속도까지 같음을 뜻하지 않는다.
용량 제한만으로 충분한 이유를 메모리 누적 방지라는 목표에 연결하면
다른 부하 조건에서도 같은 판단을 적용하기 쉬워진다.

## 요청별 평가

### 1. worktree 생성 및 발생 가능성·심각도·해결책 분석

**사용자 요청**

- 별도 worktree 생성 요청
- 상대가 받지 않아 송신 데이터가 쌓일 가능성과 심각도 분석 요청
- 수정 필요성과 적절한 해결책 제시 요청

**평가**

아직 원인이 확인되지 않은 위험을 구현 요청으로 바로 확정하지 않고,
실제로 문제가 되는지부터 판단하도록 맡긴 점이 충분했다.
사용자 표현에는 문제를 발견했다는 말이 있었지만 실제 재현 조건이나
측정 결과는 없었으므로, 대화에서 확인된 것은 위험 제기까지다.
이러한 예방 분석에는 처음부터 재현 자료를 모두 준비할 필요가 없다.

worktree 생성과 코드 조사를 위임한 것은 적절한 실행 위임이다.
문제의 존재와 수정 필요성을 AI에게 분석하게 한 것만으로
판단을 무비판적으로 맡겼다고 볼 수는 없다.

**더 효율적인 활용**

현재 요청으로 조사 시작에 충분했다.
분석을 받을 때 코드로 확인한 경로와 실제 실행으로 확인한 증상을 구분하면
원인 확정의 강도를 더 정확하게 판단할 수 있다.
이번 분석은 무제한 적재 경로를 코드로 확인한 단계였고,
수정 전 실행 재현까지 한 것으로 해석해서는 안 된다.

### 2. 오래된 메시지의 대기 시간 제한에 대한 설명 요청

**사용자 요청**

- 가장 오래된 메시지의 대기 시간을 제한한다는 의미 설명 요청

**평가**

이해되지 않은 정책을 그대로 승인하지 않고 의미를 확인한 개입은 적절했다.
이 질문으로 용량 제한과 시간 제한이 서로 다른 조건을 다룬다는 설명을
받을 수 있었다. 구현 전에 짧은 설명을 요청한 것은 불필요한 왕복이 아니다.

다만 질문하고 설명을 받았다는 사실만으로 대기 시간 계산이나
서버 송신 완료와 클라이언트 처리 완료의 차이까지 이해했다고 인정할 수는 없다.

**더 효율적인 활용**

설명을 요청한 방식으로 충분했다.
추가 구현이 필요해 보이는 경우에는 “이 대책을 빼면 원래 목표에서
무엇을 보장하지 못하는가”까지 확인하면 정책 선택의 판단력이 높아진다.
모든 내부 구현을 먼저 학습할 필요는 없다.

### 3. 용량 제한만으로 범위를 좁히는 판단

**사용자 요청**

- 모든 클라이언트에 비슷한 양을 보내므로 오래된 데이터가 천천히 쌓이기 어렵다는 의견 제시
- 바이트 상한만으로 충분한지 재검토 요청

**평가**

AI가 제시한 대책을 모두 구현하지 않고 필요성을 따진 점은
변경 범위와 복잡도를 통제한 행동이다.
특히 “맞아?”라고 재검토를 요청해 반론을 받을 여지를 남긴 점이 적절했다.

다만 근거에는 보완이 필요했다. 발신량이 비슷해도 수신 속도는 다를 수 있어
특정 연결에 오래된 데이터가 쌓이는 상황 자체를 배제할 수는 없다.
바이트 상한만으로 충분한 근거는 그 상황이 불가능해서가 아니라,
이번 목표인 무제한 메모리 누적을 상한으로 차단할 수 있기 때문이다.
AI는 결론에 동의하면서도 이 근거를 구분해 설명했다.

**더 효율적인 활용**

“목표는 무제한 메모리 누적 방지다. 바이트 상한만 적용했을 때
남는 문제가 이번 목표에 영향을 주는지 설명해줘”처럼 목표와 제외 범위를
연결하면 효율과 판단력이 높아진다.
시간 제한이 항상 불필요하다는 일반화 없이 현재 작업을 작게 유지할 수 있다.

### 4. 합의한 정책의 적용 위임

**사용자 요청**

- 바이트 상한만 적용하는 해결책의 구현 요청

**평가**

직전 대화에서 정책을 좁힌 뒤 “적용해”라고 실행을 맡긴 것은 충분한 요청이다.
사용자가 부분 송신 차감이나 안전한 삭제 지점까지 직접 설계해야 했던 것은 아니다.
이러한 구현과 시험 설계는 AI에게 위임할 수 있다.

다만 1 MiB라는 값과 구체적인 시험 조건은 AI가 선택했다.
빌드·경계 검사·실제 TCP 수신 중단 시험 통과는 AI가 제시한 근거이며,
사용자가 상한값의 적정성이나 검증 범위를 검토했는지는 대화에서 확인되지 않는다.
회고 요청을 했다는 사실을 최종 해결 확인으로 해석하지 않는다.

**더 효율적인 활용**

구현 보고를 받은 뒤 초기 정책값과 검증으로 보장된 범위를 구분해 수용하면 좋다.
이번 결과는 상한 초과 연결 종료와 정상 연결의 수신 지속을 뒷받침하지만,
정상 운영에서 1 MiB가 적절한지까지 입증하지는 않는다.
새로 모든 시험을 직접 실행하기보다 이 경계를 확인하는 것이 정확성에 도움이 된다.

## 결과 수용에 필요한 이해

**확인된 것**

- 사용자가 수정에 앞서 발생 가능성과 수정 필요성을 판단하도록 요청했음
- 이해되지 않는 시간 제한 정책의 설명을 요청했음
- AI가 제시한 대책을 모두 채택하지 않고 용량 제한만의 충분성을 재검토했음
- 용량 제한으로 범위를 좁힌 뒤 구현을 위임했음

**확인되지 않은 것**

- 같은 발신량과 서로 다른 수신 속도를 구분한 설명을 사용자가 수용했는지 여부
- 바이트 상한이 메모리 누적을 막지만 지연 시간까지 보장하지는 않는다는 이해
- `utils::send_queue()`의 헤더 포함 적재량 검사와 `Server::handle_write_locked()`의 실제 송신량 차감을 연결해 설명할 수 있는지 여부
- 순회 중 즉시 삭제하지 않고 게임 틱 끝에서 정리하는 이유에 대한 이해
- 1 MiB의 운영 적정성과 실제 게임 환경에서의 최종 결과 확인

이 항목들은 이해 부족을 뜻하지 않는다.
핵심 코드 두 경로에서 “추가 전 검사”와 “송신 후 차감”이 짝을 이루는지,
초과 연결만 정리되고 정상 연결이 유지되는지를 확인하면 결과 판단에 도움이 된다.
사용자가 보여준 강점은 정책의 필요성을 검토하고 범위를 줄인 행동이며,
서버 구현·실험 성과 자체를 사용자의 역량으로 귀속하지 않는다.
차별성은 같은 목표 중심 판단을 다른 장애나 운영 조건에도 반복 적용할 때
근거를 쌓을 수 있다.

## 다음 작업에 적용할 원칙

**추가 대책을 선택하거나 제외할 때, 불가능하다는 추측보다
지키려는 목표와 남겨도 되는 위험을 기준으로 판단한다.**

## 검토 범위

송신 대기열 누적 문제의 최초 분석 요청부터 설명 요청, 정책 범위 조정,
구현 요청과 결과 보고까지의 현재 대화를 검토했다.
근거는 대화, 해당 worktree의 변경 내역과
`docs/solve-log/2026-11-18-send-queue-limit.md`의 기록이다.
이번 회고에서는 서버 시험을 다시 실행하지 않았고,
사용자의 직접 재시험이나 운영 환경의 최종 해결 확인은 없었다.
회고·문서 저장 요청 자체와 다른 문제의 작업은 평가 범위에서 제외했다.
