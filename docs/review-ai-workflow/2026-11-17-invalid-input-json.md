# 각도·부스트 JSON 입력 방어의 AI 활용 회고

## 전체 평가

실행은 AI에 맡기되 수정의 필요성과 범위는 직접 검토한 활용이었다.
실제 장애를 겪지 않았다는 사실을 밝히고, AI가 제시한 결함이 현실적인지부터
질문했다. 구현 전에 입력 방어의 효과와 비용을 따져본 근거가 있으므로,
코드 작성을 위임했다는 이유로 의존적이라고 판단할 수 없다.

개선할 부분은 수정 후 결과를 받아들일 성공 기준을 더 명확히 하는 것이다.
검증의 설계와 실행은 AI에게 맡겨도 되지만, 보고된 검증이 목표를 충분히
다뤘는지 확인하면 결과 수용의 정확도를 높일 수 있다.

## 요청별 평가

### 1. 서버 종료 위험이 실제 결함인지 검토 요청

**사용자 요청**

- 잘못된 JSON으로 서버가 종료된다는 다른 ChatGPT의 지적 검토 요청
- 실제 발생 사례는 없음을 명시하고, 억지로 찾아낸 문제인지 판단 요청
- 해결책과 예외 처리 추가만으로 충분한지 설명 요청

**평가**

관찰된 장애와 외부에서 제기된 가능성을 구분한 요청이었다.
수정부터 지시하지 않고 실제 발생 가능성과 필요한 대응을 먼저 물은 점이
적절했다. 코드 조사와 기술적 판단을 위임하면서도 그 근거를 요구했다.
실제 재현 조건을 사용자가 미리 알아야 할 필요는 없었다.

**더 효율적인 활용**

현재 요청으로 조사 시작에 충분했다. 정상 클라이언트에서의 발생 가능성과
임의 입력으로 유발할 수 있는 위험을 나눠 보고받으면,
결함의 존재와 수정 우선순위를 구분하는 판단이 더 빨라질 수 있다.

### 2. 유한성 검사와 입력 방어 필요성 검토

**사용자 요청**

- `std::isfinite`, `1e100`, float 범위 초과의 의미 설명 요청
- 정상 각도가 어떻게 큰 숫자가 될 수 있는지 질문
- 외부 입력 방어가 끝없이 늘어날 가능성과 그럼에도 필요한지 판단 요청

**평가**

검사 함수의 뜻에서 멈추지 않고, 실제 입력 경로와 방어 비용까지 확인했다.
정상 클라이언트가 생성하는 값과 임의 전송된 값의 차이를 드러내는 데
사용자의 질문이 기여했다. 수정 필요성을 이해하기 위한 질문이었으므로
불필요한 반복으로 평가할 이유는 없다.

구현 방법은 AI에게 맡겼지만, 무엇을 방어할지에 대한 판단에는 개입했다.
다만 질문과 설명 수용만으로 수치 변환의 모든 경계 조건을
독립적으로 설명할 수 있다고 인정할 수는 없다.

**더 효율적인 활용**

개별 이상 입력을 계속 추가하기보다 허용할 메시지의 필드·타입·값 조건을
정하도록 요청하면 효율과 판단력을 높일 수 있다.
이번 대화에서도 기본 검증과 JSON 예외 처리로 범위를 좁힌 것으로 충분했다.

### 3. 구현 위임과 검증 결과 수용

**사용자 요청**

- 기본 입력 검증과 JSON 예외 처리의 필요성 설명 후 수정 요청
- 수정된 코드의 처리 흐름과 `is_object()`의 의미 설명 요청

**평가**

방어 범위를 논의한 뒤 구현을 맡긴 것은 적절한 실행 위임이었다.
수정 후에도 코드 설명을 요청하고, JSON과 객체의 차이를 구체적으로 질문해
이해가 필요한 지점을 드러냈다. 다만 설명을 받은 사실 자체가
다른 입력 처리에 적용할 능력까지 입증하지는 않는다.

AI는 수정 전 종료와 수정 후 상태 보존·정상 입력 처리를 보고했다.
메시지 처리 함수를 직접 호출한 검증이며 실제 소켓 수신 시험은 아니었다.
사용자가 이 한계를 결과 수용에 반영했는지는 확인되지 않는다.
검증 범위를 밝히고 적절한 시험을 수행하는 책임은 AI에게 있다.

**더 효율적인 활용**

성공 기준을 “잘못된 입력 후 상태가 유지되고, 이어지는 정상 입력도
처리되는가”로 확인하면 보고를 평가하기 쉬워진다.
사용자가 시험 코드를 직접 작성할 필요는 없으며, 제시된 검증과 남은 한계가
이번 수정의 수용에 충분한지 판단하는 데 집중하면 된다.

### 4. 주석·가독성 개선을 작업 지침으로 반영

**사용자 요청**

- 메시지 형식 주석을 변경한 이유 확인 후 형식과 조건을 함께 표기하도록 요청
- 코드의 논리적 작업 단위가 보이도록 간격 정리 요청
- 다음 작업에도 적용할 규칙을 제안받고 `AGENTS.md`에 추가 요청

**평가**

읽기 어려운 부분을 구체적으로 지적하고 반복 적용할 기준으로 남겼다.
일회성 수정에 그치지 않고 다음 작업의 조정 비용을 줄이는 행동이었다.
빈 줄을 통한 구분과 별도 함수 추출을 구분한 지침도 요청 범위에 적절했다.

이는 작업 방식을 개선한 사례로 평가할 수 있다.
다만 가독성 개선 요청과 지침 추가만으로 차별화된 개발 역량 전체를
입증했다고 과장할 근거는 없다.

**더 효율적인 활용**

현재 요청으로 충분했다. 이번 기준이 다음 수정에서도 유용한지 확인하고,
실제로 반복되는 불편이 있을 때만 지침을 보완하면 된다.

## 결과 수용에 필요한 이해

**확인된 것**

- 실제 장애 보고와 AI가 제기한 잠재 위험을 구분해 전달했음
- 정상 입력과 임의 입력의 차이, 방어 필요성과 비용을 판단 대상으로 삼았음
- 구현 후 코드 설명을 요구하고 JSON 값의 종류에 관한 확인 지점을 드러냈음
- 가독성 선호를 구체적인 작업 규칙으로 남겼음

**확인되지 않은 것**

- JSON 예외가 호출부와 네트워크 스레드를 거쳐 프로세스 종료로 이어지는 경로를 직접 설명할 수 있는지 여부
- 예외 처리와 값 검증이 서로 다른 실패를 막는 이유를 다른 메시지에도 적용할 수 있는지 여부
- 객체와 다른 JSON 값의 차이를 설명받은 뒤 독립적으로 적용할 수 있는지 여부
- 함수 호출 검증과 실제 소켓 수신 검증의 차이를 최종 수용에 반영했는지 여부

미확인을 이해 부족이나 무비판적 수용으로 단정하지 않는다.
AI가 수행한 원인 추적·구현·시험을 사용자의 구현 역량으로 귀속하지 않는다.

## 다음 작업에 적용할 원칙

**수정 승인 전에 왜 필요한지 확인하고, 결과 수용 전에 무엇으로 확인했는지 검토한다.**

이번에는 수정 필요성과 방어 범위의 검토가 충분했다.
다음에는 AI가 제시한 성공 기준과 검증 한계까지 명시적으로 확인하면 된다.

## 검토 범위

현재 대화의 JSON 입력 위험 분석, 방어 필요성 논의, 구현 위임,
주석·가독성 개선, 작업 지침 반영 및 코드 설명 요청을 검토했다.
근거는 실제 사용자 요청·개입과 대화에 보고된 코드 분석·실행 결과다.
회고 실행, 문서 저장 및 커밋 메시지 요청은 평가 범위에서 제외했다.

이번 회고에서는 서버 시험을 다시 실행하지 않았다.
보고된 검증은 메시지 처리 함수 호출과 서버 빌드이며,
실제 소켓 송수신 및 Unity 플레이 검증은 수행되지 않았다.
