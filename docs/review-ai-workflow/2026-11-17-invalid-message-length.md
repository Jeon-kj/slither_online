# 잘못된 메시지 길이 처리의 AI 활용 회고

## 전체 평가

재현 여부와 운영 중 발생 가능성을 함께 요구하고, 구현 전에 경계 조건을 확인한 위임은 적절했다.
수정 후에도 즉시 삭제와 지연 처리의 차이를 질문해 변경의 안전성을 검토했다.
분석·구현·시험 실행을 넓게 맡겼지만, 중요한 판단을 전부 무검토로 맡겼다고 볼 근거는 없다.

가장 유효한 개선 방향은 결과 수용 기준에 연결 종료의 게임상 영향도 포함하는 것이다.
잘못된 연결의 정리뿐 아니라 다른 플레이어에게 해당 캐릭터의 제거가 반영되는지도 구분하면
서버 내부 검증과 실제 게임 동작 사이의 빈틈을 줄일 수 있다.

## 요청별 평가

### 1. 재현과 실제 운영 발생 가능성 검증

**사용자 요청**

- `extract_message`에서 잘못된 길이 수신 후 메시지 처리가 막힌다는 문제의 재현·설명 요청
- 해결 방법과 함께 억지로 만든 문제인지 운영 중 발생 가능한지 검증 요청

**평가**

증상과 확인할 함수를 제시하고, 분석과 해결책 제안을 먼저 맡긴 범위는 충분했다.
특히 재현 성공만으로 수정 필요성을 판단하지 않고 운영상 도달 가능성까지 요구한 점이 적절했다.
비정상 입력으로 발생한다는 사실과 정상 클라이언트에서도 자연스럽게 발생한다는 주장을
구분하도록 요구한 행동이다. 재현 도구와 시험 설계를 AI에 맡긴 것 자체는 의존의 근거가 아니다.

**더 효율적인 활용**

현재 요청으로 충분했다. 결과를 읽을 때 로컬 소켓으로 실제 수신 함수를 실행한 검증과
Unity·전체 서버 루프를 실행한 검증의 차이를 수용 범위에 반영하면 판단의 정확성이 높아진다.
시험 구성의 차이를 보고하는 일은 AI의 책임이며, 사용자가 처음부터 모든 절차를 지정할 필요는 없다.

### 2. 추가 수신과 제한 초과의 경계 확인

**사용자 요청**

- 추가 수신이 필요한 경우의 처리 질문
- 제한이 10,000바이트일 때 10,001바이트 전송을 잘못된 메시지로 처리하는지 확인

**평가**

권장안을 바로 구현하도록 하지 않고, 데이터 부족과 유효하지 않은 길이의 구분을 확인했다.
이는 성공 기준과 프로토콜 해석을 검토한 개입이며 적절했다.
다만 해당 질문만으로 사용자가 선언된 본문 길이와 한 번에 수신한 데이터 크기의 차이를
독립적으로 설명할 수 있다고까지 판단할 수는 없다.

**더 효율적인 활용**

질문 자체로 충분했다. 같은 경계 확인을 다른 문제에 적용할 때도
허용된 입력의 미완성과 처음부터 허용되지 않은 입력을 구분하면 판단력이 높아진다.
이번에는 그 구분을 코드로 구현하는 작업을 AI에게 맡기는 것이 자연스러웠다.

### 3. 권장안 구현과 결과 확인

**사용자 요청**

- 설명된 권장 처리 방법에 따른 코드 수정 요청
- 수정 보고 이후 확인했다는 응답

**평가**

이미 논의된 처리 기준을 바탕으로 구현을 맡겼으므로 짧은 요청으로 충분했다.
구현 세부와 반복 시험 실행을 직접 지시하지 않은 것은 효율적인 실행 위임이다.
보고에는 잘못된 길이의 연결 종료, 정상 분할 수신과 경계값, 빌드 결과가 포함됐다.
사용자의 “확인했다”는 응답만으로 직접 실행·코드 검토의 구체적인 범위를 확정할 수는 없다.

**더 효율적인 활용**

게임 운영 관점에서 마무리할 때는 “접속 종료된 플레이어의 제거가 다른 클라이언트에도
반영되는지 확인해줘”를 추가하면 검증의 정확성이 높아진다.
이번 후속 분석에서 기존 disconnect만으로는 제거 메시지를 보내지 않는 점이 드러났으므로,
연결 정리의 성공과 게임 화면에서의 정리 성공을 구분할 가치가 있다.
이는 최초 요청에 빠진 잘못으로 볼 사안은 아니다.

### 4. 즉시 삭제와 pending 사망 처리의 차이 확인

**사용자 요청**

- disconnect는 즉시 삭제하는데 kill_slither는 pending을 사용하는 이유 질문

**평가**

기존 코드와 새 경로의 차이를 관찰하고, 삭제 시점의 안전성을 질문한 개입은 유효했다.
수정 성공 보고 이후에도 객체 수명과 실행 위치를 검토했다는 근거다.
질문으로 확인된 것은 차이를 포착하고 설명을 요구한 행동이며,
반복자 무효화와 잠금의 역할을 사용자가 독립적으로 판단할 수 있는지는 미확인이다.

**더 효율적인 활용**

현재 질문으로 충분했다. 설명을 다른 경로에 적용할 때는 컨테이너 순회 여부와
삭제 후 참조 사용 여부를 함께 확인하면 학습 효과가 높아진다.
잠금이 있다는 사실만으로 즉시 삭제의 안전성을 판단하지 않는 것이 핵심이다.

## 결과 수용에 필요한 이해

**확인된 것**

- 사용자가 재현 여부와 운영상 발생 가능성을 별도로 검증하도록 요청했음
- 추가 수신과 길이 제한 초과의 처리 기준을 구현 전에 질문했음
- 수정 후 기존 pending 사망 처리와 즉시 disconnect의 차이를 포착하고 설명을 요구했음
- 수정 보고에 대해 확인했다는 응답을 했음

**확인되지 않은 것**

- 선언된 본문 길이와 TCP 수신 단위의 차이를 독립적으로 설명할 수 있는지 여부
- 잠금, 컨테이너 순회, 삭제 후 참조 사용을 함께 고려해 다른 삭제 경로도 판단할 수 있는지 여부
- 직접 시험한 범위와 Unity·전체 게임 루프에서의 최종 동작 확인 여부
- disconnect 이후 다른 플레이어 화면의 제거 처리까지 수용 기준으로 삼았는지 여부

미확인 사항을 이해 부족이나 무비판적 수용으로 단정하지 않는다.
AI가 수행한 원인 분석과 시험 설계를 사용자가 직접 입증한 역량으로 귀속하지도 않는다.
이번 대화에서 확인된 강점은 경계 조건과 기존 동작의 차이를 질문한 판단 행동이다.
이를 다른 입력 처리와 객체 삭제 문제에도 일관되게 적용한다면 차별성의 근거가 될 수 있지만,
이번 한 사례만으로 숙련도를 확정할 수는 없다.

## 다음 작업에 적용할 원칙

**경계 조건과 삭제 시점의 안전성을 검토하고, 서버 내부 처리와 게임에서 보이는 결과를 나눠 수용한다.**

구현과 반복 실행은 AI에 맡기되, 검증이 어느 계층까지 확인했는지에 맞춰 해결 범위를 판단한다.

## 검토 범위

현재 대화의 잘못된 메시지 길이 문제에 대한 분석·구현·결과 확인·삭제 시점 질문을 검토했다.
대화에 남은 코드 조회, 로컬 소켓 시험 결과와 빌드 보고를 근거로 삼았다.
회고 과정에서는 코드를 수정하거나 시험을 다시 실행하지 않았다.
문서 작성 요청 자체는 활용 평가 대상에 포함하지 않았다.
