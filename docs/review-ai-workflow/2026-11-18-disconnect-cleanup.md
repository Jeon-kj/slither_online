# 연결 종료 처리 문제의 AI 활용 회고

## 전체 평가

구체적인 결함 후보를 제시하고 재현과 심각도 판단을 요구한 뒤,
설명이 이해되지 않자 코드 흐름을 다시 요청한 활용 방식은 적절했다.
분석·구현·시험을 넓게 맡겼지만, 판단까지 무비판적으로 위임했다고 볼 근거는 없다.

가장 보완할 부분은 수정 완료를 받아들이는 기준이다.
서버의 송신 큐에 메시지가 들어간 결과와 실제 다른 클라이언트 화면에서
객체가 사라진 결과를 구분해 최종 확인하면 판단의 정확성이 높아진다.

## 요청별 평가

### 1. 결함 후보의 재현과 해결 필요성 판단 요청

**사용자 요청**

- 정상 퇴장·사망과 EOF·송수신 오류 사이의 제거 알림 차이 검토
- epoll 등록 실패 시 소켓 미종료 문제 재현
- 과장된 문제인지 실제 해결할 문제인지 판정하고 원인·해결책 제시

**평가**

비교할 코드 경로와 의심 지점이 충분히 구체적이었다.
곧바로 수정을 지시하지 않고 실제 발생 여부와 해결 필요성을 따로 요구해,
코드상 가능성만으로 심각도를 부풀릴 위험을 줄였다.
사용자가 결함 후보를 제시한 사실은 확인되지만, 후보를 독자적으로
발견했는지와 원인까지 이해했는지는 대화만으로 판단할 수 없다.

재현 방법과 구현 판단을 AI에게 맡긴 범위도 적절했다.
AI가 선택한 오류 주입은 실패 후 처리 결함을 검증하지만,
실제 운영에서 그 오류가 얼마나 자주 발생하는지까지 입증하지 않는다.

**더 효율적인 활용**

최초 요청은 충분했다. 결과를 검토할 때에는 “실제 소켓 오류와
강제 주입한 오류를 구분하고, 각 결과가 입증하는 범위를 설명해줘”를
확인 기준으로 삼으면 정확성이 높아진다.
사용자가 오류 주입 방식까지 미리 설계할 필요는 없다.

### 2. 이해되지 않은 설명에 대한 코드 흐름 재설명 요청

**사용자 요청**

- 알림의 의미와 누락된 처리를 코드의 전후 맥락으로 설명
- TCP 연결 종료의 절차와 현재 서버가 수행하는 일·빠뜨린 일을 비교

**평가**

이해가 되지 않는 지점을 명확히 밝히고, 추상적인 결론을 실제 코드 경로로
연결하도록 요구한 개입이었다. 설명을 받은 사실만으로 이해했다고
처리하지 않은 점은 판단의 주도권을 유지하는 행동이다.

특히 “연결 종료”와 “다른 플레이어에게 제거를 알리는 것”을 구분해 달라는
요청은 수정의 필요성을 판단하는 데 직접 도움이 됐다.
다만 설명 이후 사용자가 원리를 자신의 말로 정리한 근거는 없으므로,
핵심 동작을 이해했는지는 미확인으로 남겨야 한다.

**더 효율적인 활용**

현재 요청으로 충분했다. 학습을 더 남기고 싶다면 다음에는 짧게
“소켓을 닫아도 다른 연결에는 게임 메시지가 자동 전달되지 않으니
공통 정리 함수에서 별도로 알려야 한다는 뜻인가?”처럼 자신의 해석을
확인하는 방법이 있다. 질문 횟수를 늘리는 것보다 오해를 확인하는 데 유용하다.

### 3. 설명 후 구현 실행 위임

**사용자 요청**

- 제시된 해결책 실행

**평가**

앞선 대화에서 수정 방향과 이유를 설명받은 상태이므로,
짧은 실행 지시로 구현을 맡긴 것은 충분했다.
사용자가 코드 작성·빌드·경계 사례 시험을 다시 세세하게 지시할 필요는 없다.
작업 지침에도 검증과 해결 기록 작성이 이미 포함돼 있었다.

다만 최종 근거는 AI가 실행한 서버 함수·소켓 시험과 송신 큐 검사다.
사용자가 실제 Unity 화면에서 해결을 확인한 기록은 없다.
이는 실행 위임이 과도했다는 뜻이 아니라, 확인된 해결 범위가
서버 측 검증까지라는 의미다.

**더 효율적인 활용**

최종 수용 시 “A를 정상 퇴장 메시지 없이 종료했을 때 B 화면에서
A가 사라지는지” 한 번 확인하면 제품 동작까지 연결된다.
사용자가 직접 실행하거나 AI에게 실행을 맡길 수 있다.
핵심은 직접 수행 여부가 아니라 실제 화면 검증과 서버 검증의 차이를
알고 수용하는 것으로, 판단의 정확성을 높이는 방법이다.

## 결과 수용에 필요한 이해

**확인된 것**

- 사용자가 정상 퇴장·사망과 통신 종료 경로를 비교 대상으로 지정했음
- 재현과 실제 해결 필요성 판단을 함께 요구했음
- 설명이 충분하지 않다고 판단해 코드 흐름과 TCP 절차의 설명을 추가 요청했음
- 설명 이후 제시된 수정의 실행을 승인했음

**확인되지 않은 것**

- TCP 소켓 닫기, 서버 상태 삭제, 다른 클라이언트 객체 삭제를 독립된 처리로 설명할 수 있는지 여부
- closing 플래그 설정만으로는 close()가 실행되지 않는다는 점과 조기 반환의 관계를 이해했는지 여부
- 제거 알림을 공통 경로로 옮길 때 중복 알림·입장 전 종료·알림 중 추가 실패를 고려해야 하는 이유를 이해했는지 여부
- 실제 Unity 환경에서 다른 플레이어의 객체 제거를 확인했는지 여부

이 항목들은 이해 부족의 증거가 아니다.
결과를 판단할 핵심 코드 지점은 disconnect_client_locked()의 정리 후 알림과,
modify_epoll_events()의 실패 후 공통 정리 호출이다.
재현·원인 분석·경계 사례 검증은 AI가 수행한 작업이며,
그 자체를 사용자의 구현 역량으로 귀속하지 않는다.

이번 대화에서 드러난 역량은 결함 경로를 구체적으로 비교하고
해결 필요성과 설명의 충분성을 검토하는 행동이다.
이를 차별성으로 주장하려면 다른 문제에서도 같은 판단을 재현하고
실제 결과까지 확인한 근거가 더 필요하다.

## 다음 작업에 적용할 원칙

**구현은 넓게 위임하되, 검증 결과가 실제로 보장하는 범위를 확인한 뒤 수용한다.**

이번에는 송신 큐의 제거 메시지와 다른 클라이언트 화면의 객체 삭제,
오류 주입의 성공과 실제 오류 발생 빈도를 각각 구분하는 것이 그 기준이다.

## 검토 범위

현재 대화의 연결 종료 알림 누락·epoll 소켓 누수에 대한 분석 요청,
코드 흐름 설명 요청, 구현 실행 위임을 검토했다.
이후 solve-log 확인과 이번 리뷰 요청은 별도 평가 대상으로 확장하지 않았다.
대화와 앞서 확인한 코드·검증 기록을 근거로 작성했으며,
이번 회고에서 서버 시험이나 Unity 검증을 다시 실행하지 않았다.
