# 봇 일괄 종료 문제의 AI 활용 회고

## 전체 평가

재현 명령과 비교 조건을 제시하고, 분석을 받은 뒤 재현·수정·재시험을 맡긴 흐름은 적절했다. 세 요청만으로 과도한 의존이라고 판단할 근거는 없다. 개선할 부분은 직접 실행하는 비중을 늘리는 것이 아니라, 원인을 확정할 증거와 해결을 인정할 성공 기준을 더 명확히 요구하는 것이다.

## 요청별 평가

### 1. 증상·재현 조건·원인 추측 전달

**사용자 요청**

- 봇 20개를 초당 5개씩 접속시킨 뒤 Ctrl+C로 종료하면 서버도 간헐적으로 종료된다는 증상과 실행 명령 제공
- Unity 클라이언트 종료는 정상이며 봇 1개에서는 오류를 관찰하지 못했다는 비교 조건 제공
- 멀티스레드 종료 처리 문제를 예상 원인으로 제시

**평가**

발생 행동과 비교 조건이 구체적이어서 조사 시작에 충분했다. “내 예상”이라는 표현으로 관찰과 원인 추측을 구분했으며, 특정 방식으로 수정하라고 제한하지 않은 점도 적절했다. 이는 단순히 해결을 떠넘긴 요청이 아니라 사용자가 확보한 관찰을 바탕으로 분석을 위임한 요청이다.

**더 효율적인 활용**

추가 정보를 모두 수집한 뒤 질문할 필요는 없었다. 다만 간헐적 오류에서는 “1개에서는 발생하지 않았다”를 미관찰 결과로 유지하고, 발생 불가능한 조건으로 단정하지 않는 것이 중요하다. 현재 요청도 미관찰 사실을 전달하는 수준이므로 큰 수정이 필요하지 않다.

### 2. “원인을 분석하고 보고해”

**사용자 요청**

- 코드 수정에 앞서 원인 분석과 보고 요청

**평가**

원인 설명을 먼저 받고 구현 여부를 다음 단계에서 결정하는 위임은 적절했다. 특히 간헐적 오류에서는 그럴듯한 설명만으로 수정에 들어가는 일을 줄이는 데 도움이 된다. 다만 분석 보고를 요청했다는 사실만으로 사용자가 원인의 타당성을 직접 검토했다고 인정할 수는 없다.

**더 효율적인 활용**

“확인된 사실과 가설을 구분하고, 원인을 확정하려면 무엇을 관측해야 하는지 설명해줘”를 덧붙이면 좋다. 분석 결과를 검증 가능한 주장으로 받아볼 수 있어, 추측을 확정처럼 수용할 위험을 줄인다. 모든 조사 단계를 사용자가 설계할 필요는 없다.

### 3. 기존 봇 탐색·재현·수정·재시험·트레이드오프 보고

**사용자 요청**

- 클라이언트 위치에서 bot_client를 찾아 오류 재현
- 수정 후 재시험 및 트레이드오프 보고

**평가**

실제 재현과 수정 후 시험을 모두 요구했고 변경의 불이익까지 확인하려 했으므로 위임 범위는 적절했다. 코드 작성과 반복 실행을 AI에게 맡긴 것은 실행의 위임이며, 그 자체로 의존적이라는 근거가 되지 않는다. 다만 “재시험 통과”를 무엇으로 판단할지 구체화하지 않아 시험 설계와 성공 기준을 AI가 정할 여지가 컸다. 이것이 곧 무비판적 수용을 뜻하지는 않는다.

**더 효율적인 활용**

다음처럼 성공 기준을 추가하면 보고를 평가하기 쉬워진다.

> 수정 전 종료 원인을 관측하고, 수정 후 같은 연결 오류가 발생해도 서버가 유지되는지 확인해줘. 이후 새 봇의 접속과 게임 진행까지 확인해줘. 원래 재현 절차를 바꿨다면 차이도 밝혀줘. 현재 코드에서 생기는 실제 불이익을 중심으로 보고해줘.

이는 단순 반복 성공과 원인에 대한 방어 검증을 구분하고, 재현 절차가 달라졌을 때 검증 범위를 판단하는 데 도움이 된다. 다만 SIGPIPE나 EPIPE를 미리 알고 요청할 필요는 없으며, 구체적인 관측 대상은 AI가 분석을 통해 제안해도 된다.

## 결과 수용에 필요한 이해

**확인된 것**

- 사용자가 재현 조건과 비교 대상을 구분해 보고했음
- 분석과 구현을 나눠 요청하고, 수정 후 시험과 변경 영향 보고를 요구했음
- 이후 SIGPIPE 통지의 실제 활용 여부를 질문하여 과장된 트레이드오프 설명을 검토했음. 이는 결과 수용 방식을 보여주는 보조 근거이며 별도 요청 평가로 범위를 확장하지 않음

**확인되지 않은 것**

- 사용자가 SIGPIPE 종료와 EPIPE 반환의 차이 및 기존 연결 정리 경로를 직접 설명할 수 있는지 여부
- 수정 후 EPIPE에도 서버가 생존했다는 관측이 단순 반복 통과보다 강한 근거인 이유를 이해했는지 여부
- 실제 환경에서 직접 재시험하거나 최종적으로 해결을 확인했는지 여부

확인되지 않은 이해를 이해 부족이나 과도한 의존으로 단정할 수는 없다. 결과를 판단할 때는 “오류를 숨겼는가, 기존 오류 처리를 실행하게 했는가”와 “원래 실패 상황이 수정 후에도 관측됐는가”를 확인하면 충분하다. AI가 수행한 원인 추적과 구현을 사용자의 시스템 프로그래밍 역량으로 귀속하지 않는다.

## 다음 작업에 적용할 원칙

**분석 단계에서는 원인을 확정할 증거를 요구하고, 구현 단계에서는 성공 기준을 확인한 뒤 실행을 위임한다.**

세 요청을 반드시 하나로 합치거나 모든 명령을 직접 실행할 필요는 없다. 이번 경험에서 확인되는 강점은 구체적인 문제 보고와 변경 영향에 대한 검토이며, 일반적인 위임만으로 차별성을 주장하기보다는 이런 판단을 다른 문제에도 적용할 수 있는지가 중요하다.

## 검토 범위

사용자가 지정한 세 요청을 중심으로 대화와 기존 실행 결과를 검토했다. 이후 문서 규격 수정과 리뷰 지침 개선 과정은 평가 대상에서 제외했다. 이번 회고에서 서버 시험을 다시 실행하지 않았다.
