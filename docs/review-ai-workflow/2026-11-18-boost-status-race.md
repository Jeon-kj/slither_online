# boost_status 데이터 경합 문제의 AI 활용 회고

## 전체 평가

공유 변수의 접근 차이를 직접 발견하고, AI가 제시한 결론을 자신의 실행 모델과
비교해 다시 질문한 활용 방식이 적절했다. 분석과 설명을 받은 뒤 구현을 맡겼으므로,
단순히 수정 결과를 받아들인 흐름으로 볼 수 없다. 구현을 넓게 위임했다는 이유로
의존적이라고 판단할 근거도 없다.

개선할 지점은 질문의 양보다 검증 결과를 구분하는 기준이다. 이번 수정은 잠금 범위의
코드 검토와 빌드로 확인됐으며, 실제 실행에서 경합을 검출하거나 증상을 재현한 것은
아니다. 이 차이를 이해하고 수용하면 필요한 검증 수준을 더 정확하게 판단할 수 있다.

## 요청별 평가

### 1. 잠금이 없는 쓰기가 실제 문제인지 검증 요청

**사용자 요청**

- 별도 worktree 추가 요청
- 네트워크 스레드는 boost_status를 잠금 없이 쓰고 게임 스레드는 잠금 안에서 읽는다는 관찰 전달
- 동기화가 필요 없을 것이라는 생각을 밝히고 실제 문제인지 검증 요청

**평가**

변수, 실행 주체, 읽기·쓰기 방식의 차이를 제시해 조사 시작에 충분했다.
자신의 생각을 확정된 원인으로 강요하지 않고 검증 대상으로 제시한 점도 적절했다.
사용자가 발견한 접근 차이와 AI가 확인한 상위 호출의 잠금 범위는 구분해야 한다.
후자의 추적까지 사용자가 직접 수행했다고 볼 근거는 없다.

분석과 worktree 구성을 맡긴 것은 적절한 실행 위임이다. 다만 “검증”이라는 말만으로
정적 분석과 실행 재현 중 무엇을 기대했는지까지 확정되지는 않는다.

**더 효율적인 활용**

“문제가 성립하는 코드 경로와 실제 실행에서 확인한 결과를 구분해줘”를 덧붙이면
정확성과 결과 판단력이 좋아진다. 그렇다고 최초 요청에 검증 도구나 재현 프로그램까지
지정할 필요는 없다. 필요한 방법과 한계는 AI가 제안해야 한다.

### 2. 이전 값이나 새 값을 읽어도 되는데 왜 문제인지 재질문

**사용자 요청**

- 읽기 직전이나 직후에 값이 바뀌어도 게임 동작상 상관없다는 반례 제시
- mutex가 필요한 이유와 C++ 언어 규칙과의 관계 설명 요청
- 이해 후 기존에 배운 가시성 개념과의 연결 확인

**평가**

이번 작업에서 판단의 주도권이 가장 명확히 드러난 요청이다. 해결책을 안다는 사실과
문제를 이해했다는 사실을 구분하고, 자신의 모델에서 모순되는 부분을 구체적으로
질문했다. 일반적인 “더 쉽게 설명해줘”보다 쟁점이 선명했다.

이 질문으로 게임이 허용하는 반영 지연과 C++이 보장하는 메모리 접근을 분리하는
설명을 얻었다. 이어서 가시성이라는 기존 개념과 연결한 행동도 확인됐다.
다만 사용자가 메모리 모델 전체를 설명할 수 있다고까지 평가할 근거는 없다.

**더 효율적인 활용**

현재 질문 방식으로 충분했다. 같은 방식의 다음 단계로는 “값 자체의 전달만 보면
atomic으로 충분한데, 우리 코드에서는 왜 mutex인가”를 확인할 가치가 있다.
이는 컨테이너와 객체 수명까지 판단 범위를 넓혀 다른 사례에 적용하는 데 도움이 된다.
이 내용을 이미 이해하지 못했다고 단정하는 제안은 아니다.

### 3. 설명을 이해한 뒤 해결 요청

**사용자 요청**

- 동기화 문제에 관한 설명을 받은 후 수정 실행 요청

**평가**

이미 기존 mutex를 쓰는 최소 수정안과 이유를 공유한 상태였으므로 짧은 구현 요청으로
충분했다. 사용자가 같은 조건을 반복하거나 구현 명령을 세세하게 지정할 필요는 없었다.
앞선 재질문 없이 원인 판단까지 전부 맡긴 흐름과도 다르다.

AI는 쓰기와 조회를 같은 mutex로 보호하고, 삭제된 항목을 재생성하지 않도록 수정했다.
서버 빌드는 통과했지만 실행 중 경합의 수정 전후 검출은 하지 않았다.
사용자가 이 검증 한계를 별도로 평가하거나 실제 환경에서 최종 확인했는지는
대화에서 확인되지 않는다. 이후 문서 요청이 곧 무비판적인 코드 수용을 뜻하지는 않는다.

**더 효율적인 활용**

완료 보고를 판단할 때는 “빌드 성공 외에 어떤 근거로 경합이 없어졌다고 보는가”를
확인하면 좋다. 이 사례에서는 같은 mutex 안의 조회·쓰기와 읽기·삭제, 상위 호출의
잠금 해제 여부를 대조하는 것이 핵심이다. 경합 검사기 실행을 무조건 요구하기보다
코드로 확인한 보장과 실행에서 미확인인 부분을 나눠 판단하면 효율이 좋아진다.

## 결과 수용에 필요한 이해

**확인된 것**

- 사용자가 공유 변수의 쓰기와 읽기에서 잠금 적용이 다르다는 점을 발견했음
- 이전 값으로 한 틱 처리해도 된다는 게임 요구를 구체적으로 설명했음
- 해결책만 받아들이지 않고 자신의 모델과 설명의 차이를 질문했음
- 설명 후 이해했다고 표현하고 기존 가시성 개념과 연결을 시도했음

**확인되지 않은 것**

- 데이터 경합과 가시성을 구분하고, 일반 bool과 atomic의 보장 차이를 직접 설명할 수 있는지 여부
- client_contexts의 삭제와 operator[]의 재생성 때문에 bool만 atomic으로 바꾸는 것으로 충분하지 않음을 이해했는지 여부
- 수정 후 코드의 잠금 범위와 빌드 결과를 직접 검토하거나 실제 게임에서 확인했는지 여부

미확인 사항은 이해 부족의 증거가 아니다. 결과 수용에 필요한 핵심은
“부스트 값이 이전 값이어도 된다”는 요구가 유지되는 동시에, 객체 조회부터 갱신까지
게임 스레드의 접근 및 삭제와 조율된다는 점이다. 경합 검출이 없었다는 사실과
소스 코드의 동기화 근거가 없다는 주장은 구분해야 한다.

## 다음 작업에 적용할 원칙

**내가 허용하는 동작과 언어·자료구조가 보장하는 동작을 나눠 질문하고,
수정 후에는 그 보장을 확인한 근거를 받아본다.**

이번 대화의 강점은 자신의 모델을 명시하고 AI의 결론을 검토한 행동이다.
이를 다른 공유 상태나 객체 수명 문제에도 적용할 수 있다면 실무 판단력의 근거가 된다.
이번 한 사례만으로 동시성 전문성이나 성능 개선 성과를 주장할 근거는 없다.

## 검토 범위

현재 대화의 boost_status 검증 요청, 개념 확인 질문, 수정 위임과 완료 보고를
평가했다. solve-log 내용과 앞서 확인한 코드 및 빌드 결과를 보조 근거로 사용했다.
이후 문서 위치·중요 표시 조정과 이번 회고 요청은 요청별 평가에 포함하지 않았다.
이번 회고에서 서버 실행이나 경합 검사를 다시 수행하지 않았다.
