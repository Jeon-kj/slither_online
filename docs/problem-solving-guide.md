# 문제 해결 기록 규격

문제 해결 기록을 작성하거나 수정할 때 이 규격을 따른다.
`2026-11-13-slither-interpolation.md`를 간결한 기록의 참고본으로 사용한다.

## 작성 원칙

- 하나의 문제는 하나의 문서로 관리한다. 실패와 재시도도 같은 문서에 합친다.
- 문서 상단에는 문제 요약과 원인 및 해결을 간략히 적는다. 요청은 해결 과정에만
  포함하고 별도 항목으로 중복하지 않는다. 긴 프롬프트 원문이나 대화 전체는 복사하지 않는다.
- 해결 과정은 원인 후보, 조사 방향, 수정 결과가 달라진 지점을 중심으로 나눈다. 같은 목적의 연속 요청은 한 단계로 합친다.
- 필요한 단계에서 `사용자 요청`과 `결과`의 글머리 목록으로 흐름을 정리하되,
  모든 대화에 같은 형식을 반복 적용하지 않는다. 사소한 대화와 반복 답변은 생략한다.
- 검증 한계와 부가 설명은 확인 결과에 모은다. 해결 과정에는 다음 판단이나 요청에 영향을 준 내용만 남긴다.
- 해결 과정의 항목은 명사형 또는 `~했음`, `~그러함` 등의 간결한 기록체로 끝낸다.
  서술형 문단으로 대화를 다시 풀어 쓰지 않는다.
- 확인된 사실, 가설, 사용자 확인 결과를 구분한다.
- `변경 파일` 위에 `조언` 항목을 둔다. 후보 선정·제외의 근거, 조사 순서,
  수정과 검증 방식에서 더 나은 방향이 있다면 근거와 대안을 간결하게 적는다.
  사용자 요청과 에이전트 판단 모두 검토하며, 제안할 내용이 없으면 비워둔다.
- 변경 내용은 파일명과 “기존의 무엇을 어떻게 바꿨는지”를 한 줄로 적는다.
  상세 구현, 수식, 전체 호출 순서는 반복하지 않는다.
- 호출·실행 순서는 실제 변경된 경우에만 변경점과 이유를 짧게 적는다.
- `문제 요약` 아래에 `문제 발생 조건`을 하위 항목으로 둔다. 문제가 있던 버전에서
  어떤 환경·설정·행동으로 증상이 나타났는지 적는다. 재현은 코드를 되돌리는 방법을
  뜻하지 않는다. 확인된 조건과 추정 조건을 구분하고, 확인되지 않은 필수 조건은 만들지 않는다.
- 재현 기록만을 위해 별도 프로그램이나 임시 검증 스크립트를 만들지 않는다.
  기존 빌드·테스트가 필요하면 실행하되, 문서에는 결과와 미검증 사항을 요약한다.
- 임시 파일 경로, 재실행 명령, 원본 결과·스크립트 목록은 기본적으로 생략한다.
  성능 측정 등 별도 요구사항에 필요한 근거는 해당 요구사항을 따른다.

## 문서 틀

```markdown
# 문제 제목

## 문제 요약

관찰된 증상을 간략히 요약한다.

### 문제 발생 조건

- 문제가 있던 버전의 실행 환경과 관련 설정
- 증상을 일으킨 행동과 관찰 결과
- 사용자 보고와 직접 확인, 추정 조건을 구분해 기록

## 원인 및 해결

핵심 원인과 해결 방법을 간략히 요약한다. 원인이 확정되지 않았다면 가설임을 표시한다.

## 해결 과정

### 1. 최초 요청과 분석

**사용자 요청**

- 조사할 증상과 비교 대상 확인 요청
- 분석 또는 수정 범위 지정

**결과**

- 확인된 사실과 원인 가설 정리

### 2. 후속 요청과 재시도

**사용자 후속 요청**

- 추가 관찰 전달 및 기존 가설 재검토 요청

**결과**

- 새 단서에 따른 판단 수정
- 수정 후 증상 유지 또는 해소 등 다음 판단에 영향을 준 결과 요약
- 실패 여부 또는 사용자 해결 확인 기록

## 조언

문제 해결 흐름에서 개선할 판단과 근거, 다음에 적용할 대안을 간략히 적는다.
제안할 내용이 없으면 이 항목은 비워둔다.

## 변경 파일

| 파일 | 변경 내용 |
|---|---|
| 경로/파일명 | 기존 동작을 어떤 동작으로 바꿨다. |

## 확인 결과

전체 검증 범위, 사용자 확인, 남은 한계와 부가 설명을 모아 적는다.
```

작업에 없는 단계나 불필요한 항목은 생략하되, `조언` 제목은 유지한다.
